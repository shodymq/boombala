# Миграция потока заявок: Telegram-only → PostgreSQL + CRM + Telegram

Работающий процесс **не ломается**: новый путь включается флагом `LEAD_PIPELINE` и откатывается им же. Production не меняется
без подтверждения владельца. Сбор персональных данных в базу в production не включается до отдельного решения о законном
размещении (см. `SUPABASE-ADAPTATION.md`).

## 1. Сегодня (режим `telegram-only`, по умолчанию)

```
Форма ─POST /api/lead─> сайт: валидация → (память) защита от дублей → Telegram sendMessage → 200
```
Слабые места: нет постоянного хранилища; защита от дублей и лимиты живут в памяти одного экземпляра; заявка есть только в чате.

## 2. Целевой поток (режим `dual`)

```
Форма ─POST /api/lead (Idempotency-Key)─> сайт: валидация, лимиты
        └─ server-to-server ─> platform /api/intake/lead (Bearer, constant-time)
              ┌─────────────── ОДНА транзакция PostgreSQL ───────────────┐
              │ 1. idempotency: ключ уже есть → вернуть прежний результат │
              │ 2. upsert contact (по телефону + имени, без слияния чужих)│
              │ 3. INSERT lead_request                                    │
              │ 4. INSERT consent_event (версия документа согласия)       │
              │ 5. INSERT outbox (topic telegram.lead, ссылка на lead_id) │
              └───────────────────────────────────────────────────────────┘
              COMMIT ─> 201 {ok, leadId}      ← успех только после подтверждённой записи
              └─ попытка отправки (≤ 4 c, не обязательная для ответа) ─> Telegram
Повторы: outbox drain (по расписанию и «попутно») ─ FOR UPDATE SKIP LOCKED, backoff, max N попыток
Сайт: ответ платформы 2xx → показать «Заявка отправлена».
      Платформа недоступна (сеть/5xx/таймаут) → резерв: прежний прямой Telegram (режим dual) и пометка в логе.
```

Принципы:
- **Outbox в той же транзакции** как данные: заявка не может сохраниться без задачи уведомления и наоборот. Никаких «фоновых
  задач serverless после ответа».
- **В outbox только ссылка** (`lead_id`), не персональные данные: текст сообщения собирается при отправке из актуальной записи.
- **Идемпотентность:** `idempotency_key` (UUID, генерируется в форме при открытии) с уникальным индексом. Повтор того же ключа
  возвращает прежний `leadId`, второй заявки и второго сообщения нет. Параллельные дубликаты разрешаются уникальным индексом.
- **Telegram недоступен:** заявка сохранена, outbox остаётся `pending` с `next_attempt_at`; при восстановлении сообщение уходит ровно
  один раз (повторная отправка исключена статусом `sent` + блокировкой строки).
- **Логи** содержат код ошибки и id, но не имя/телефон и не токены.

## 3. Режимы и откат

| `LEAD_PIPELINE` | Поведение | Когда |
|---|---|---|
| `telegram-only` (по умолчанию) | Как сейчас | Production сегодня |
| `dual` | База+CRM основное; Telegram через outbox; при недоступности платформы прямой Telegram как резерв | После решения о размещении ПДн и интеграционной проверки |
| `strict` | Только база; при недоступности платформы заявка не принимается | По желанию, позже |

Откат: вернуть `LEAD_PIPELINE=telegram-only` (новое развёртывание/Instant Rollback на Vercel). Данные в базе остаются.
Исторические Telegram-заявки в CRM автоматически **не импортируются**.

### Расхождение при падении платформы (режим `dual`)

Если платформа недоступна, сайт отправляет заявку прямым Telegram, чтобы она не потерялась. Такая заявка **есть только в Telegram и
не сохранена в CRM**. Система не делает вид, что она в CRM:
- сообщение в Telegram содержит строку «⚠️ ТОЛЬКО В TELEGRAM: в CRM не сохранена…» и не содержит «CRM №»;
- в логах сайта запись `[lead] platform path failed (…)` без персональных данных.

Редкий случай: платформа сохранила заявку, но ответ потерялся (таймаут). Тогда сайт тоже уйдёт в резерв: в Telegram придут два сообщения
(одно с «CRM №», второе с пометкой), а в CRM заявка будет одна. Поэтому в пометке сказано сначала проверить CRM по номеру.

Восстановление: после возврата платформы сотрудник ищет клиента по номеру в разделе «Клиенты»; если нет, вносит вручную.
Не реализовано: форма ручного добавления заявки в CRM и импорт из Telegram (в бэклоге). Исторические Telegram-заявки в CRM
автоматически не переносятся. Строгий режим `strict` исключает расхождение ценой отказа в приёме при падении платформы.

## 4. Схема данных (миграция `004_crm.sql`, схема `bb`, RLS включён)

| Таблица | Назначение |
|---|---|
| `legal_documents` | Версионированные документы: `kind`, `version`, `title`, `body`, `status` (draft/approved/published/retired), даты, кто утвердил. Опубликованный текст неизменяем (триггер). Документ с пометками `[ТРЕБУЕТСЯ …]` опубликовать нельзя |
| `contacts` | `id`, `name`, `phone_e164`, `source` (первое появление), `first_registered_at`, `last_activity_at`, `phone_verification` (`unverified`), `marketing_opt_in=false`. Идентичность контакта = телефон + имя (без регистра/лишних пробелов). **Тот же телефон с другим именем = другой контакт**, интерфейс показывает «тот же номер у N контактов» |
| `lead_requests` | Заявка (форма дня рождения): пакет, комната, дата, дети, страница, UTM, `idempotency_key` (уникален), `status`, `contact_id` |
| `consent_registrations` | Событие QR-регистрации (имя, телефон, источник `qr`), `idempotency_key`, `contact_id`. Не равно фактическому посещению |
| `consent_events` | История согласий: `contact_id`, `document_id` (конкретная версия), `event` given/revoked, `method` (`web_checkbox`), `occurred_at`, `ip_hash`, `user_agent`, ссылка на заявку/регистрацию |
| `outbox` | `topic`, `ref_id`, `status` (pending/sending/sent/dead), `attempts`, `next_attempt_at`, `locked_until`, `last_error_code`, `sent_at` |
| `export_log` | Кто, когда, формат, диапазон дат, столбцы, число строк, IP — факт каждой выгрузки |
| `users.can_export` | Разрешение на выгрузку для сотрудника (Owner всегда может) |

Единое отображение в CRM: заявки и QR-регистрации — **разные события** одного контакта (таймлайн).

## 5. Порядок внедрения

1. Применить миграции к **тестовому** проекту Supabase (прямое подключение), проверить RLS-тест.
2. Задеплоить `platform` на Vercel с `PII_INTAKE_ENABLED=0`; создать Owner.
3. Утвердить и опубликовать юридические документы (владелец + юрист); решить вопрос законного размещения.
4. Включить `PII_INTAKE_ENABLED=1` на платформе, затем `LEAD_PIPELINE=dual` на сайте; наблюдать журнал и Telegram.
5. Включить `CONSENT_FORM_ENABLED=1` и разместить QR.

## 6. Что проверяется локально (интеграционные тесты)

Заявка появляется в CRM и в Telegram (мок); Telegram недоступен, заявка сохранена; повторная отправка не создаёт дубль
(в том числе параллельная); после восстановления Telegram уведомление уходит один раз; QR создаёт контакт и запись согласия с
версией документа; разные люди с одним телефоном не сливаются; экспорт доступен только Owner/разрешённому, неавторизованный
блокируется и не логируется как выгрузка; CSV/XLSX без formula injection; старый режим `telegram-only` работает как раньше.
