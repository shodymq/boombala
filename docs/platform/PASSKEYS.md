# Вход через Face ID / Touch ID (passkeys, WebAuthn) для CRM

Ежедневный вход сотрудника: открыть CRM → «Войти с Face ID / Touch ID» → подтвердить лицом, отпечатком или кодом устройства. Два действия, без почты, пароля и шестизначных кодов.
Пароль + код из приложения и коды восстановления остаются **запасным входом**. CRM доступна только из VPN (WireGuard); обработчики passkeys живут только в админке.
По умолчанию выключено: без `PASSKEYS_ENABLED=1` нет ни кнопок, ни страниц, ни обработчиков (404).

Связанные документы: [инструкции владельцу и кассиру](PASSKEYS-GUIDES.md), [чек-лист выпуска, откат и список для проверки безопасности](PASSKEYS-ROLLOUT.md).

## Как это устроено
- Библиотека `@simplewebauthn/server` и `@simplewebauthn/browser` 14. Собственной криптографии нет.
- Ключ создаётся **с обязательной проверкой человека** (`userVerification: required`), поэтому вход ключом считается пройденным вторым фактором (подходит под `MFA_MODE=required`).
- В базе только открытый ключ, id ключа и счётчик (миграция `014_passkeys.sql`): по выгрузке войти нельзя.
- Право `RBAC`, журнал аудита и ограничение по числу ошибок работают как раньше; ошибки входа ключом считаются в том же ограничителе, что и неверные пароли.

## Первый доступ нового сотрудника (никогда по одному паролю)
1. Владелец создаёт сотрудника (имя, e-mail, роль, начальный пароль) в «Сотрудники».
2. Владелец нажимает **«Выдать код настройки»** (нужно подтверждение самого Owner'а: код из приложения или ключ). Показывается одноразовый код `XXXX-XXXX-XXXX`, действует 2 часа, хранится только хэш. Владелец передаёт его **лично**.
3. Сотрудник вводит e-mail + пароль → «Нужен код настройки» → вводит код. Только после этого показывается секрет приложения-аутентификатора (раньше он показывался любому, кто знает пароль).
4. Сотрудник включает приложение-аутентификатор (оно остаётся запасным входом), получает 10 кодов восстановления и входит.
5. В «Мой пароль» → «Добавить это устройство» (подтверждение кодом из приложения) → Face ID / Touch ID.
Пять неверных кодов настройки сжигают код; неверные попытки считаются в общем ограничителе.

## Включение (делает администратор сервера; в Production не включалось)
1. Миграция `014` (`npm run db:migrate`), затем **роли ещё раз** (`npm run db:roles`), затем `npm run preflight`. Правило «код настройки для первого фактора» вступает в силу сразу после применения 014 (даже при `PASSKEYS_ENABLED=0`).
2. В `admin.env` (только админка; в `api.env` и `site.env` они запрещены):

   | Переменная | Значение |
   |---|---|
   | `PASSKEYS_ENABLED` | `1` |
   | `WEBAUTHN_RP_ID` | имя хоста админки без схемы и порта, например `crm.boombala.kz` |
   | `WEBAUTHN_ORIGINS` | точные адреса, **https**, например `https://crm.boombala.kz` |
   | `WEBAUTHN_RP_NAME` | необязательно, подпись в окне устройства |
   | `STAFF_SESSION_IDLE_MINUTES` | необязательно, 5–720; для общего планшета кассы 30–60 (по умолчанию 720) |

3. Приложение проверяет конфигурацию само (иначе админка в `kz-production` не стартует, в журнал идут только коды без значений); `preflight` тоже проверяет её и наличие миграции.
4. Нужен действующий HTTPS-сертификат на `crm.boombala.kz` (и в VPN). RP ID и origin нельзя менять после выдачи ключей: ключ привязан к RP ID.
5. Откат: `PASSKEYS_ENABLED=0` и перезапуск `bb-admin` (ключи остаются в базе, вход по паролю и коду не затронут).

## Подтверждение личности перед чувствительным действием (step-up)
Добавить или отозвать ключ, отозвать все ключи сотрудника, выдать код настройки можно только после **свежего** подтверждения: текущий код из приложения / код восстановления, либо ключ. Подтверждение привязано к человеку, к текущей сессии и к одному действию, живёт 5 минут и тратится при использовании. Украденной cookie недостаточно. Серверных действий без этой проверки нет (отзыв ключей и выдача кода только через проверяемые обработчики).

## Потеря устройств и восстановление
| Ситуация | Что делать |
|---|---|
| Потерян iPhone, есть Mac/другой ключ | Войти другим устройством → «Мой пароль» → «Отозвать» у потерянного (подтвердить). Или Owner: «Сотрудники» → «Отозвать все ключи» (завершает и его сессии) |
| Потерян Mac | то же |
| Сотрудник уволен | Owner: «Отключить» + «Отозвать все ключи» |
| Нет ни одного ключа, есть приложение | вход по паролю + коду |
| Нет ни ключей, ни приложения, есть коды восстановления | пароль + код восстановления, затем новое устройство |
| Потеряно всё (сотрудник) | Owner: «Сбросить второй фактор» (отзывает и ключи) → «Выдать код настройки» → сотрудник настраивается заново |
| Потеряно всё у единственного Owner | на сервере (root, по VPN или консоль хостинга): `npm run user:mfa-reset -- --email …` (отзывает и ключи), затем `npm run user:enrollment-code -- --email …`; после пароля + кода настройки Owner включает приложение и устройства заново. Каждое действие в аудите «server_console» |
Сброс второго фактора всегда отзывает и passkeys: обхода после одного пароля нет. Нельзя отозвать **свой последний** способ входа без запасного (приложения). Рекомендуется иметь **двух** Owner'ов.

## Общий планшет кассы
Не регистрируйте ключи на общем планшете: ключ принадлежит человеку, а не устройству. Сотрудник входит **своим** телефоном: в окне Safari выбрать «Использовать другое устройство / Scan QR code» и подтвердить на своём iPhone (нужен Bluetooth рядом) либо личным аппаратным ключом. «Выйти» = смена пользователя. `STAFF_SESSION_IDLE_MINUTES=30..60` закрывает забытую сессию.

## Что записывается в аудит
`passkey.registered`, `passkey.revoked`, `passkey.revoked_all`, `passkey.register_failed`, `auth.login` (с `passkey: true`), `auth.passkey_failed`, `auth.stepup`, `auth.stepup_failed`, `enrollment.code_issued`, `enrollment.code_redeemed`, `enrollment.code_failed`, `mfa.reset` (с числом отозванных ключей). Секреты, коды настройки, id ключей и challenge в журнал не попадают.

## Команды
`npm run passkeys:revoke -- --email …` (все ключи одного человека), `npm run user:enrollment-code -- --email …`, `npm run user:mfa-reset -- --email …`.
