# Первый vertical slice админки: заявки (leads list + смена статуса)

**Статус:** контракт и тесты готовы. Переключения нет: ни одного runtime-флага и ни одной строки поведения CRM не меняется. Блокеры ниже должны быть решены до переключения.

## 1. Что уже проверено на реальных ответах
Источник: `BoomBalaApp` `origin/main` (9b65ae5), тесты `test_admin_lead_inbox_endpoints.py`, ответы сняты через `TestClient` с теми же данными сидов.
Файлы: `platform/tests/fixtures/admin-leads/*.json`. Тесты: `platform/tests/leads-fastapi.test.ts` (9 pass).

| Операция | Метод и путь | Ответ |
|---|---|---|
| вход | `POST /api/v1/admin/auth/login` | 200 |
| список | `GET /api/v1/admin/leads` (+ `branchId`, `status`) | 200 `{items[], total}` |
| карточка | `GET /api/v1/admin/leads/{id}` | 200 (расширенная карточка с `email`, `notes`, `contactMethod`) |
| смена статуса | `PATCH /api/v1/admin/leads/{id}/status` | 200 (карточка после изменения) |
| нет токена | любая | 401 `authentication_required` |
| неверный статус | PATCH | 422 `validation_error` |
| нет заявки | GET карточки | 404 `lead_not_found` |

Список содержит имя и телефон клиента. Это ожидаемо для сотрудника, но доступ обязан проверяться по роли и филиалу (см. блокер 3).

## 2. Почему нельзя переключить сейчас (блокеры)

**B1. Два хранилища заявок.** Сайт и `platform` пишут в `bb.lead_requests` (CRM Next.js). FastAPI принимает `/mobile/leads/*` и публичные заявки в свою таблицу. Пока оба пишут, список FastAPI неполный, а список CRM не видит заявок из приложения. Двойной записи быть не должно: каждая заявка имеет ровно одного писателя. Решается N11 (единый intake), см. `docs/platform/ADMIN-MIGRATION-MAP.md`.

**B2. Два набора сотрудников.** `bb.users` (роли `owner`, `manager`, `editor`, MFA TOTP) и `admin_users` в FastAPI (роли `super_admin`, `operator`, `sales_manager`, область филиала у `operator`). Один человек не должен иметь два входа с разной защитой. Варианты: (а) SSO из FastAPI в CRM, (б) перенос пользователей с MFA, (в) оставить два и запретить правки в обеих. Решение владельца.

**B3. Словарь статусов.** Платформа: `new | in_progress | confirmed | cancelled | completed`. FastAPI: `new, contacted, qualified, booked, paid, completed, lost, in_progress, confirmed, cancelled, closed`. Предложенная таблица — в `src/core/leads-fastapi.ts` (`PROPOSED_CRM_STATUS`). Неизвестный статус — ошибка, а не строка. Таблицу утверждают владелец и Codex.

**B4. Идентификаторы заявок.** У платформы UUID, у FastAPI строки (`lead-new`). Для сверки нужна таблица соответствия `crm_lead_id ↔ fastapi_lead_id` с происхождением (provenance), без склейки по телефону.

**B5. Паритет доступа.** Список FastAPI отдаёт телефоны и имена. Проверить, что роли и область филиала FastAPI не шире, чем у `requests.manage` в CRM.

## 3. Порядок работ (один слайс за раз)
1. **Контракт и тесты** — сделано (этот PR).
2. **Решения B1–B5** — владелец и Codex. Без них дальше не идти.
3. **Shadow-чтение**: CRM читает список из FastAPI и сравнивает с `bb.lead_requests` (только чтение, без записи), расхождения пишутся в лог.
4. **Переключение чтения** за флагом `ADMIN_LEADS_SOURCE=platform|fastapi` (по умолчанию `platform`). Откат — возврат флага.
5. **Переключение записи статуса** — только после того, как чтение совпало на staging. Пока писатель один: либо CRM, либо FastAPI, никогда оба.
6. Аудит: смена статуса пишется в тот же аудит, что и сейчас.

## 4. Правила, которые не обсуждаются
- Одна заявка — один писатель в каждый момент времени.
- При недоступности FastAPI список CRM показывает ошибку, а не пустую очередь.
- Неизвестный статус или поле не угадываются.
- Цена, телефон и имя не копируются в логи.
