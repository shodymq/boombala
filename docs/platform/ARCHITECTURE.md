## 2. Варианты архитектуры

### Вариант A. Монолит на Vercel + управляемая облачная БД (Neon/Supabase/Vercel Postgres)
Админка как раздел `/admin` или второй Vercel-проект из того же репозитория, Postgres у зарубежного провайдера.
- (+) Минимальная сложность, ноль администрирования серверов, деплой как сейчас.
- (−) **Персональные данные (имена, телефоны, согласия) уходят за пределы Казахстана.** Закон РК «О персональных данных и их защите» требует хранить базы персональных данных граждан РК на серверах в РК. Это прямо противоречит вашему требованию.
- (−) Сессии админки на `*.vercel.app` и API на другом домене: сторонние cookie в Safari.

### Вариант B (выбран). Отдельное приложение платформы в Казахстане + публичный сайт остаётся на Vercel
Новое приложение `platform/` (Next.js, админка и API в одном проекте) на VPS в Казахстане вместе с PostgreSQL 16 (Docker Compose: app, postgres, reverse proxy с TLS, cron-бэкапы).
- Админка: **отдельное приложение на отдельном нейтральном домене**, доступное только через VPN (решение заменило ранний вариант «поддомен сайта»; см. `ADMIN-ISOLATION-KZ.md`). Cookie сессии привязана к хосту админки и не используется публичным сайтом.
- Публичное API: `api.boombala.kz` (или `/api/public/*` на том же хосте) с CORS-allowlist `https://boombala.kz`.
- Публичный сайт читает цены, доступность и новости с API; **формы с персональными данными (бронь, `/consent`) отправляются из браузера напрямую на KZ-API**, не через Vercel.
- (+) Данные в РК; Vercel не видит новых ПДн; тот же стек и код-стиль, что у сайта; один проект админки и API без дублирования.
- (+) Не нужны Redis, очереди, микросервисы: лимиты и сессии живут в PostgreSQL.
- (−) Нужно администрировать VPS: обновления ОС, TLS, бэкапы, мониторинг.
- (−) Небольшая фиксированная ежемесячная плата за VPS (стоимость зависит от провайдера и тарифа, уточняется).

### Вариант C. Всё на Vercel, но БД на KZ-хостинге по публичному TLS-соединению
- (−) Динамические IP Vercel → БД открыта в интернет; задержка 100–200 мс на запрос, проблемы с пулом соединений serverless; ПДн всё равно проходят через Vercel (США/ЕС).
- Отклонён.

### Вариант D. Полностью перенести сайт тоже на VPS
Отклонён: лишний риск для работающего сайта без выгоды.

**Решение: B.** Критерии: безопасность и локализация ПДн (B лучше всех), сложность (B средняя, A минимальная), стоимость (B: VPS), поддержка (один стек Next/TypeScript, одна команда). Юридическую оценку локализации и трансграничной передачи подтверждает юрист оператора; технически B даёт соблюдение по хранению и уход ПДн с Vercel.

> До выбора KZ-хостинга платформа разрабатывается и тестируется локально на реальном PostgreSQL. Код не привязан к провайдеру: Docker + `DATABASE_URL`.

## 3. Безопасность (сквозные требования)

- Пароли: **argon2id** (`@node-rs/argon2`), минимум 12 символов; фиктивная проверка хэша при неизвестном e-mail (выравнивание времени ответа).
- Сессии: непрозрачный случайный токен 256 бит, в БД только его SHA-256; cookie `__Host-` (HttpOnly, Secure, SameSite=Lax, Path=/); абсолютный срок 7 дней, простой 12 часов; ротация при входе; отзыв при выходе, смене пароля, смене роли, деактивации.
- Вход: лимит попыток в PostgreSQL по паре (e-mail, IP) и по IP; ответ не различает «нет пользователя» и «неверный пароль».
- Авторизация: **только на сервере** (DAL: каждая функция принимает пользователя и проверяет право). `proxy.ts` делает лишь оптимистичную проверку наличия cookie.
- CSRF: мутации только POST через Server Actions (проверка Origin встроена) и route handlers с явной проверкой Origin/Host; SameSite=Lax.
- XSS: React-экранирование, **никакого `dangerouslySetInnerHTML` для пользовательского контента**, CSP с nonce, `X-Frame-Options: DENY`, `nosniff`, HSTS.
- Аудит: append-only таблица `audit_log` (триггер запрещает UPDATE/DELETE); пишутся входы, подтверждения/отмены, цены, роли, публикации.
- Секреты: только переменные окружения сервера, не в Git, не в клиентском bundle; `server-only` на модулях доступа к БД.
- Публичные POST: rate limit в PostgreSQL, идемпотентность по `Idempotency-Key`, honeypot.
- Резервные копии: nightly `pg_dump` + шифрование + копия на второй носитель, проверка восстановления (план в `OPERATIONS.md`, реализация в Этапе 5).
- 2FA (TOTP) для Owner: рекомендуется после MVP, схема её допускает.

## 4. Модель данных

Все id пакетов и комнат стабильные (`wow-party`, `roblox-room`, …). Время хранится в `timestamptz`, даты слотов в `date`, зона бизнеса `Asia/Almaty`.

### Этап 1 (реализован): ядро и каталог
- `users(id uuid, email citext unique, name, password_hash, role, is_active, created_at, last_login_at)`, `role ∈ owner|manager|editor`
- `sessions(id uuid, token_hash bytea unique, user_id, created_at, expires_at, last_seen_at, revoked_at, ip, user_agent)`
- `login_attempts(id, email_norm, ip, success, at)`
- `audit_log(id bigserial, at, actor_user_id, action, entity_type, entity_id, before jsonb, after jsonb, ip, user_agent)` (append-only)
- `packages(id text pk, name, sort_order, is_active)`
- `rooms(id text pk, name, sort_order, is_active)` (удалять нельзя, только деактивировать, и только без будущих броней)
- `time_slots(id smallint pk 1..3, starts_at time, ends_at time)`: ровно 10:00–14:00, 14:00–18:00, 18:00–22:00
- `price_rules(id, package_id, rule_type base|weekday|date, rule_date, amount_kzt, created_by, created_at)`: **append-only история**; текущее значение = последняя запись на (пакет, тип, дата). Иерархия: цена на дату → будничная → обычная. `amount_kzt NULL` для типа `date` снимает особую цену.

### Этап 2: QR и CRM
- `legal_documents(id, kind visit_rules|personal_data, version, title, body, status draft|published|retired, published_at)` версионированные тексты; **до утверждённого текста окончательный документ не публикуется**
- `consent_registrations(id, name, phone_e164, rules_doc_id, pd_doc_id, method 'web_checkbox', submitted_at, ip_hash, user_agent, source 'qr', idempotency_key)`
- `contacts(id, phone_e164, display_name, first_registered_at, last_registered_at, registrations_count)`: группировка по **непроверенному** номеру, без объединения личностей
- `consent_events(id, registration_id, event revoked|corrected, at, by_user, note)` отзыв и исправление
- маркетинговое согласие отдельным полем в будущем; рассылки сейчас не отправляются

### Этап 3: бронирование
- `booking_requests(id, public_ref, package_id, requested_date, slot_id, room_id, parent_name, phone_e164, pd_doc_id, quoted_price_kzt, status new|in_progress|confirmed|cancelled|completed, assigned_to, created_at, idempotency_key unique)`
- `slot_reservations(id, slot_date, slot_id, room_id, kind booking|block, booking_request_id, reason, price_snapshot_kzt, created_by, created_at, released_at, released_by)`
  - **`UNIQUE (slot_date, slot_id, room_id) WHERE released_at IS NULL`**: одна активная запись на комбинацию. И бронь, и ручная блокировка занимают её, поэтому конфликтуют на уровне PostgreSQL
  - триггер запрещает занимать слот, который уже начался (`Asia/Almaty`)
- `booking_status_history`, `booking_notes`

Заявка не блокирует комнату. Подтверждение = транзакция: `SELECT … FOR UPDATE` заявки, затем `INSERT INTO slot_reservations`: при нарушении уникальности возвращается понятный конфликт 409.

### Этап 4: новости
- `news_posts(id, slug unique, title, excerpt, body, cover_url, status draft|published, publish_at, unpublished_at, created_by, updated_by, created_at, updated_at)`; тело хранится как простой текст/ограниченная разметка, рендер без сырого HTML.

| Утечка ПДн | БД в РК, шифрованные бэкапы, роли, аудит, без ПДн в Telegram-уведомлениях новой системы |
| Секреты в Git | `.env*` в `.gitignore`, `.env.example` без значений, сканер секретов перед коммитом |

## 7. Что потребуется от вас

1. **Хостинг в Казахстане:** VPS (2 vCPU / 4 ГБ / 40+ ГБ SSD, Ubuntu LTS) у казахстанского провайдера с доступом по SSH и публичным IPv4. Решение провайдера.
2. **Домен:** управление DNS `boombala.kz` (записи `admin.` и `api.`).
3. **Первый Owner:** e-mail владельца (пароль задаётся командой при установке, в чат не пересылается).
4. **Юридические тексты:** утверждённые правила посещения и согласие на обработку ПДн (с версиями) от юриста; политика обработки ПДн, оператор и ответственный.
5. **Хранилище бэкапов:** второй носитель в РК (S3-совместимое хранилище или второй сервер).
6. **Резервные способы связи:** доступ к DNS и Telegram-боту остаются прежними.
7. Решение по **обложкам новостей**: на первом этапе обложка задаётся ссылкой на изображение, загрузка файлов на сервер платформы появится позже (см. ограничения в Этапе 4).

Ничего из этого не нужно для локальной разработки Этапа 1.
