## 2. Две группы функций

### A. Можно выпускать независимо от юридического согласования QR (нет данных посетителей)
- Сайт: `/`, `/attractions`, `/birthdays` (контент и цены), `/menu`, `/news`, `/news/[slug]`, `/news/img/[id]`, `/sitemap.xml`, `/privacy` (без изменений).
- Платформа, только контентный модуль: вход, `/news*`, `/news/media`, `/api/media*`, `/account`, `/users`, `/audit`, `/api/health`; роли Owner и Editor; публикация и снятие новостей, `revalidate` сайта.
- Условие: **форма заявки остаётся как сегодня** (`telegram-only`, без изменений). Она относится к группе B, но её поведение в этом выпуске не меняется.

### B. Требуют отдельного разрешения на работу с реальными данными
- Сайт: `/consent`, `/api/consent`, `/api/lead` (в режимах `dual` и `strict`), календарь в форме (`/api/availability`, привязан к БД бронирований).
- Платформа: `/contacts*`, `/requests`, `/bookings` (данные клиентов), `/export` и `/api/export`, `/retention`, `/legal` и `/api/public/legal`, `/api/intake/*`, `/api/public/availability`, `/api/cron/outbox`, отзыв согласия и обезличивание.

Учётные записи сотрудников (email, имя, IP) входят в A, но это тоже персональные данные: см. юридический вопрос 6.

## 3. Целевая архитектура

```
Посетитель ──► boombala.kz (Vercel, статический/ISR сайт, только контент)
     │             │  читает: новости, занятость (без ПДн)
     │             ▼
     └─ POST (форма заявки, QR) ──► api.boombala.kz  ─┐   КАЗАХСТАН
                                                       ├─ Платформа (Next.js, self-host) ─► PostgreSQL (primary)
Сотрудник ──────────────────────► admin.boombala.kz ──┘          │                           │
                                                                 ├─ outbox worker ─► Telegram (только «minimal»)
                                                                 └─ бэкапы (WAL + дамп) ─► хранилище КЗ, второй ЦОД
```

| Компонент | Роль после перехода |
|---|---|
| **Vercel** | Только публичный сайт (статика/ISR) и Preview. Не принимает и не проксирует ПДн: форма уходит напрямую на `api.boombala.kz`. Функции `/api/lead`, `/api/consent` отключаются после переключения. Переменные окружения без секретов ПДн |
| **Платформа и БД (КЗ)** | API приёма, CRM-админка, новости, бронирования, outbox, PostgreSQL, бэкапы, мониторинг. Единый источник истины. `admin.` и `api.` на одном приложении |
| **Telegram** | Только канал оповещения. Рекомендация: `TELEGRAM_NOTIFY_LEVEL=minimal` («новая заявка №N», без имени и телефона; детали в CRM). Токен хранится только на стороне КЗ. Исторические сообщения с ПДн в чате остаются вне контроля платформы |
| **Supabase `boombala-test`** | Только тестовая/staging БД с синтетическими данными. **Не продвигается в Production** (создана для тестов, Франкфурт) |
| **База мобильного приложения** | Не затрагивается |

Почему одна платформа в КЗ, а не «контентная админка на Vercel + CRM в КЗ»: два приложения с двумя БД удваивают роли, миграции и сопровождение, а контентные данные малы и переносятся дёшево. Но выпуск группы A **не ждёт** КЗ-инфраструктуры (этап 1 ниже).

Сохранение защиты от конфликтов: двойное бронирование блокируется **PostgreSQL**, а не приложением (частичный уникальный индекс на `(slot_date, slot_id, room_id) WHERE released_at IS NULL`, триггеры, снимок цены). Это переносится вместе со схемой на любой PostgreSQL 15+ с **одним primary** (без multi-writer). Тесты `e2e:booking` и `verify:remote` обязательны на новой БД до запуска.

## 4. Проверенные риски переезда (найдено в коде)

| Находка | Риск | Что сделать |
|---|---|---|
| `platform/src/server/request.ts` берёт IP из `x-vercel-forwarded-for`, затем `x-real-ip`, затем `x-forwarded-for` | При self-host клиент сам задаст `x-vercel-forwarded-for` и подделает IP (хеш IP в истории согласий, лимиты) | За nginx перезаписывать единственный заголовок и доверять только ему; убрать ветку `x-vercel-*` для не-Vercel окружения |
| `@vercel/oidc` и заголовок `x-vercel-trusted-oidc-idp-token` в `lib/platform.ts` и `server/api.ts` | Нужен только для защищённых Preview; в КЗ OIDC нет (код уже терпимо возвращает пустой токен) | Оставить для Preview, в Production полагаться на общий секрет и allowlist; убрать зависимость позже |
| Публичный приём требует `Bearer PLATFORM_INTAKE_TOKEN` | Браузер не может хранить секрет, а форма должна идти напрямую в КЗ | Новый публичный эндпоинт приёма без секрета: CORS allowlist, лимиты (nginx `limit_req` плюс приложение), honeypot, проверка Origin, лимит тела, bot-защита без сторонних сервисов (например, proof-of-work), идемпотентность (уже есть) |
| Rate limit на сайте в памяти экземпляра | Неэффективен на serverless | На одном узле КЗ эффективен; плюс `limit_req` |
| Расчёт на поведение Vercel: `PLATFORM_HTTPS`, cookie `__Host-`, HSTS | Нужны на self-host | TLS и HSTS на nginx, `PLATFORM_HTTPS=1` |
| Next.js 16 `next start`, `sharp` (обработка новостных картинок), нативные зависимости (`@node-rs/argon2`) | Нужна сборка под архитектуру сервера | Собирать на самом сервере или в контейнере; зафиксировать версии |
| Логи приложения | Только коды и id (проверено) | Сохранить; логи сервера без тел запросов |
| Supabase-специфика (RLS, роли anon/authenticated) | В обычном PostgreSQL безвредна | Оставить, проверить `harden_schema()` на чистом PostgreSQL (покрыто тестами) |

## 5. Миграции Production

Production-БД ещё **нет** (есть только `boombala-test`). Новая БД в КЗ создаётся пустой.
Порядок строго по именам, штатным раннером (checksum, advisory lock, отдельная транзакция на файл), через прямое/сессионное подключение:

| № | Файл | Что делает |
|---|---|---|
| 001 | `001_core.sql` | пользователи, сессии, попытки входа, аудит (append-only) |
| 002 | `002_catalog.sql` | пакеты, комнаты, слоты, цены |
| 003 | `003_private_schema.sql` | закрытая схема `bb`, RLS |
| 004 | `004_crm.sql` | контакты, заявки, QR-регистрации, юридические документы, история согласий, outbox, журнал выгрузок |
| 005 | `005_function_search_path.sql` | фиксирует `search_path` функций |
| 006 | `006_bookings.sql` | бронирования, защита от двойного бронирования |
| 007 | `007_news.sql` | новости и изображения |
| 008 | `008_optional_qr_phone.sql` | телефон необязателен только у QR |
| 009 | `009_consent_revocation.sql` | обезличивание, охрана истории согласий, настройки retention (автообработка выключена) |

Затем: `seed` каталога (пакеты, комнаты, цены с даты), создание Owner (`create-user`), `verify` и тесты брони. Юридические документы создаются **черновиками**; публикация только после утверждения юристом.
Для группы A (этап 1, текущий стек) достаточно тех же 001–009 в чистой БД: таблицы ПДн существуют, но пусты и недоступны (см. этап 1).
Миграции не редактируются после применения (checksum). Откат: восстановление из бэкапа, а не «обратные» миграции.

## 6. Резервное копирование, восстановление, мониторинг, секреты

**Бэкапы.** Непрерывная архивация WAL (pgBackRest или WAL-G) плюс ночной полный бэкап в хранилище **в КЗ**; вторая копия в другом ЦОД/городе КЗ; шифрование на стороне клиента (age/GPG), ключ отдельно. Ориентиры: RPO ≤ 5 мин, RTO ≤ 2 ч (уточнить с владельцем). Срок хранения 14–30 дней.
**Восстановление.** Скрипт `platform/scripts/backup-restore-check.mjs` уже доказывает, что бэкап поднимается с теми же данными и защитой (индекс брони, триггеры, RLS). План: ежемесячная проверка восстановления на отдельном сервере с записью результата.
**Связь с правом на удаление.** Бэкап хранит данные до ротации: срок хранения бэкапов = максимальная задержка полного стирания (указать юристу). После восстановления обезличивания нужно применить заново по списку из `audit_log` (`contact.anonymized`): для этого предусмотрен отдельный скрипт (в плане, этап 3).
**Мониторинг.** Внешний uptime-пробник (`/api/health`, плюс главная страница и `api.`), метрики БД (диск, соединения, репликационный лаг), успешность бэкапов (алерт «нет свежего»), число `dead` в outbox, доля ошибок 5xx, срок сертификата. Алерты в отдельный Telegram-канал **без ПДн**. Логи JSON без тел запросов, хранение 30 дней.
**Секреты.** В репозитории секретов нет (проверялось сканом перед каждым коммитом). В КЗ: `EnvironmentFile` с правами 0600 или Docker secrets; DB-роли минимальных прав (приложение без DDL, отдельная роль миграций, роль «content» без прав на таблицы ПДн); SSH только по ключам, 2FA на панели хостинга; регламент ротации для `DATABASE_URL`, `PLATFORM_INTAKE_TOKEN`, `CRON_SECRET`, `PLATFORM_IP_PEPPER` (при смене pepper хеши IP в старой истории перестают сопоставляться, это ожидаемо), токена Telegram. На Vercel остаются только публичные переменные сайта и секрет `revalidate`.

**Этап 0. Решения (без кода).** Владелец и юрист отвечают на вопросы раздела 9 (особенно 1–4). Выбор провайдера КЗ. Подтверждение, что «существующая PostgreSQL» понята верно.

## 9. Юридические вопросы, которые техника сама не решает

1. Требование размещения баз ПДн граждан РК на серверах в РК: что именно считается «хранением» и «обработкой» (передача через CDN/функции Vercel, Telegram, GA/Meta), нужна ли локализация для всей цепочки или только для БД.
2. Допустима ли сегодняшняя схема (имя и телефон в Telegram через сервер за рубежом) до перехода, и что делать с уже накопленными сообщениями в Telegram.
3. Достаточность срока 12 месяцев для QR; сроки хранения закрытых заявок и броней (в том числе бухгалтерские); решение о допуске без регистрации.
4. Правовая роль: оператор (ИП «Аманов»), поручение обработки хостинг-провайдеру КЗ, договор, уведомления/реестры, ответственный за ПДн; реквизиты для документов (ФИО, ИИН, адрес).
5. Видеонаблюдение, документы на аттракционы, школьные группы: как они отражаются в документах V3.3 (не новые функции).
6. Персональные данные самих сотрудников (email, имя, IP): допустимо ли держать их за рубежом на этапе 1, или нужны обезличенные служебные учётные записи.
