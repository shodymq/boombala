# Face ID / Touch ID: исправленные уязвимости, чек-лист выпуска, откат, проверка безопасности

Состояние: код и тесты готовы (PR #30). В Production **не включалось и не сливалось**. PR #29 (другая реализация) не использовать: у обоих PR миграция `014_passkeys.sql`, применяться должна только одна.

## Что исправлено
| Было / риск | Стало |
|---|---|
| **Первая регистрация по одному паролю.** Кто узнал пароль нового сотрудника, входил, видел секрет TOTP и регистрировал свой телефон | Первый фактор (приложение или ключ) включается только с **одноразовым кодом Owner'а** (12 знаков, хэш, 2 часа, 5 попыток, привязан к человеку и к сессии). Без него секрет не показывается, подтверждение первого кода отклоняется. Код выдаётся после step-up Owner'а; для аварий есть консольная команда |
| **Украденная cookie добавляет/снимает ключи** | Step-up: добавление и отзыв ключа, массовый отзыв, выдача кода требуют свежего подтверждения (код приложения/восстановления или ключ), привязанного к человеку, сессии и действию, на 5 минут, одноразового. Старые серверные действия без проверки удалены |
| **Блокировка Owner** | Passkey добавляется только при включённом приложении-аутентификаторе (запасной вход). Нельзя отозвать свой последний способ входа без запасного. Сброс второго фактора отзывает и passkeys (обхода по одному паролю нет), новый вход только с новым кодом. Консольное восстановление: `user:mfa-reset` + `user:enrollment-code` (аудит `server_console`) |
| **Гонка счётчика, отзыв во время входа** (найдено тестом) | Обновление счётчика условное и атомарное; ключ и человек перепроверяются в той же транзакции; взаимоблокировка параллельных входов устранена (блокировка строки пользователя) |
| Повтор ответа, чужой origin/RP ID, нет проверки человека, чужой ключ, чужой user handle, ключ на странице второго фактора другого человека | Отказ (тесты на каждый случай) |
| Фиксация сессии | Каждый вход выдаёт новый токен; ожидающая сессия гасится; подсунутый cookie не становится сессией |
| Общий планшет | Свой телефон/ключ у каждого; `STAFF_SESSION_IDLE_MINUTES`; инструкция |

4. **Сборка** из `main` после слияния (workflow `release-artifact`, Linux x86_64). Развернуть **в новый каталог релиза**, не поверх: платформа (`bb-admin`, `bb-api`) отдельно от сайта. Сайт PR #30 не меняет.

6. **Приватный доступ к `crm.boombala.kz`:** приватная DNS-запись только внутри WireGuard (split-DNS, публичной записи нет), nginx слушает адрес VPN, сертификат TLS (Let's Encrypt через DNS-01 или внутренний CA, доверенный на устройствах), `ALLOWED_HOSTS=crm.boombala.kz`, `ADMIN_ALLOWED_CIDRS` = сеть VPN. Проверить `deploy/kz/scripts/verify-isolation.sh`.
7. **Включить**: в `admin.env` `PASSKEYS_ENABLED=1`, `WEBAUTHN_RP_ID=crm.boombala.kz`, `WEBAUTHN_ORIGINS=https://crm.boombala.kz`, при необходимости `STAFF_SESSION_IDLE_MINUTES`; `preflight` без ошибок; перезапустить **только** `bb-admin`.
8. **Owner:** вход по паролю и коду → «Мой пароль» → добавить iPhone и Mac (step-up). Проверить вход «Войти с Face ID / Touch ID» (два действия), выход, повторный вход. **Проверить восстановление:** отозвать ключ, войти по паролю+коду, добавить заново; убедиться, что коды восстановления сохранены; завести второго Owner'а.
9. **Менеджер:** создать, выдать код настройки лично, пройти первый вход, добавить его телефон. Проверить права (нет «Сотрудники», «Журнал», «Выгрузка»).
10. **Касса:** `/attendance` (поиск, подтверждение, исправление), `/consent` и сайт не изменились, QR-регистрации идут. Общий планшет: вход чужим телефоном, «Выйти».
11. **Недоступность из интернета:** с внешней сети `https://crm.boombala.kz` не разрешается/не отвечает, `admin`-пути на публичном сайте 404, порты 3100/3101/5432 закрыты, SSH только по ключам.
12. Через сутки: журнал аудита без `auth.passkey_failed` всплесков, `bb-admin` без ошибок.

## План отката
- **Мгновенно (без отката кода и базы):** `PASSKEYS_ENABLED=0`, перезапуск `bb-admin`: вход по паролю и коду как раньше; ключи остаются в базе.
- **Код:** вернуть симлинк `/opt/boombala/platform` на предыдущий релиз, перезапустить `bb-admin`/`bb-api`. Миграция 014 обратно совместима со старым кодом (добавлены только таблицы и колонка); откатывать базу не нужно. Старый код не знает кода настройки: новые сотрудники в этом режиме настраиваются как раньше.
- **База:** восстановление из проверенной копии шага 3 только если повреждены данные (не ожидается).
- Если Owner заблокирован: консоль сервера, `user:enrollment-code` / `user:mfa-reset` (см. PASSKEYS.md).

## Список для независимого ревью безопасности
1. `src/core/enrollment.ts`: код (энтропия, хэш, TTL, попытки, одноразовость, привязка к сессии), `mayEnroll` в `completeMfaLogin` и на странице `/login/mfa`; нельзя ли получить секрет TOTP без кода.
2. `src/core/stepup.ts`, `src/core/passkeys.ts`: привязка grant к человеку/сессии/действию, срок, атомарное потребление; **нет** серверных действий, меняющих ключи без него (`rg "revokePasskey|revokeAllPasskeys|issueEnrollmentCode" src` — вызывают только обработчики `api/webauthn/*`, `api/auth/*` и консольные скрипты).
3. WebAuthn: challenge (32 байта библиотеки, БД, 5 минут, `DELETE … RETURNING`), origin и RP ID из окружения, `userVerification: required`, user handle, условный `UPDATE` счётчика, блокировка пользователя, отзыв во время входа, повтор ответа.
4. HTTP-слой: проверка `Origin`, JSON, размер, `proxy.ts` (публичны только `/api/webauthn/login/*`), класс пути `admin` (только VPN-хост), 401 без сессии, отсутствие утечек в ответах.
5. Ограничения: `lockedFor` (`passkey@<ip>`), лимит открытых challenge, лимит ключей, ограничитель кода настройки и step-up.
6. Данные и права БД: `014_passkeys.sql`, `db:roles` (нет прав у `bb_api`), аудит без секретов, `STAFF_SESSION_IDLE_MINUTES`.
7. Профиль `kz-production` (`exposure.ts`): https, RP ID/origin, запрет переменных в `api`/`site`.
8. Тесты: `passkeys.test.ts`, `passkey-security.test.ts` (реальная проверка подписи программным аутентификатором), `e2e/passkeys.e2e.mjs` (настоящий Chromium, виртуальный аутентификатор), `isolation`, `kz-flow`.
9. Операционное: консольные команды и их аудит; рекомендация двух Owner'ов.

## Ручные проверки (нельзя выполнить удалённо, это **не** PASS)
Нужны физический iPhone/Mac и рабочий VPN:
1. iPhone Safari: добавить устройство (Face ID), выйти, «Войти с Face ID / Touch ID», подтвердить вход.
2. macOS Safari (Touch ID / iCloud-связка): то же; синхронизированный ключ с iPhone виден на Mac.
3. Закрыть браузер полностью, открыть CRM: сессия жива до окончания idle/срока; после выхода: вход ключом.
4. Отключить и подключить WireGuard: вход ключом работает (ключ не привязан к IP).
5. Добавить второе устройство, отозвать первое: первое не входит, второе входит.
6. Потеря устройства: Owner отзывает ключи; сотрудник входит по паролю и коду.
7. Общий планшет: вход чужим iPhone через «Использовать другое устройство», «Выйти».
