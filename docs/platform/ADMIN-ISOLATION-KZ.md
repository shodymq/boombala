# Production в Казахстане: изоляция админки, VPN, MFA, роли БД

Статус: **подготовка архитектуры, конфигураций и тестов в `release/preview`.** Ничего не развёрнуто: Production, `main`, DNS, реальные данные, флаги сбора ПДн и Telegram не менялись, домен и сервер не покупались, настоящих адресов в репозитории нет (только примеры `example.test`, `10.77.0.0/24`, `198.51.100.10`).

## 0. Принятые решения

1. **Весь Production веб-контур Boom Bala размещается в Казахстане (Production целиком в Казахстане):** публичный сайт, API, админка, PostgreSQL, очередь уведомлений, резервные копии. **Vercel (и Supabase `boombala-test`) используются только для тестового Preview.** Это заменяет прежнюю схему «сайт на Vercel, API и БД в КЗ».
2. Первый запуск: **один VPS в КЗ, ориентир 4 vCPU / 8 ГБ RAM**, с раздельными процессами (три системных пользователя), раздельными ролями БД и **внешними резервными копиями**.
3. Админка на **отдельном нейтральном домене** (выбирается и покупается позже), **без публичной DNS-записи**, только через **self-hosted WireGuard**. Сертификат через **ACME DNS-01**.
4. Второй фактор: **TOTP** в первой версии. WebAuthn не внедряется.
5. Админка не живёт на домене публичного сайта: ни на нём самом, ни на его поддомене, ни по пути вида `/admin`; публичный сайт не содержит маршрутов админки и входа сотрудников.
6. Миграция `010_mfa.sql` применена к `boombala-test` (после проверки, со снимком контрольных данных); Production не затрагивался.

## 1. Схема подключения (один VPS)

```
 ИНТЕРНЕТ                                      ОДИН VPS В КАЗАХСТАНЕ (4 vCPU / 8 ГБ)
 ─────────                                     ──────────────────────────────────────────────────────────────────
 Посетитель ─► <домен сайта>:443 ─► nginx (публичный адрес) ─► bb-site  127.0.0.1:3000   пользователь bbsite
                  только страницы и 3 маршрута сайта:                │  PLATFORM_URL=http://127.0.0.1:3101
                  /api/lead, /api/consent, /api/availability         ▼  (секрет сайта ↔ API)
                  жёсткие лимиты, тело ≤ 8 КБ, остальное /api/ — 404
                                                          bb-api  127.0.0.1:3101   пользователь bbapi
                                                          (НЕТ публичного listener и имени)   БД-роль bb_api
                                                                          │  только функции bb.intake_*
 Сотрудник ─ WireGuard UDP 51820 ─► wg0 10.77.0.1 ─► nginx (адрес VPN, НЕ публичный) ─► bb-admin 127.0.0.1:3100
 (телефон/компьютер,                    <ДОМЕН АДМИНКИ>:443, allow 10.77.0.0/24            пользователь bbadmin, MFA обязателен
  одно устройство = один ключ)          без публичной DNS-записи                           БД-роль bb_admin
                                                                                                  │
                                              PostgreSQL 127.0.0.1:5432 (только изнутри) ◄────────┘
 Таймер systemd (loopback) ─► bb-admin /api/cron/outbox ─► Telegram (уведомления, только из процесса админки)
 pgBackRest ─► (шифрованные копии) ─► внешнее S3-хранилище КЗ + второй хост КЗ (SFTP) — вне этого сервера
```

| Откуда | Куда | Порт | Разрешено |
|---|---|---|---|
| интернет | публичный адрес | 443 (и 80: редирект и ACME) | только сайт |
| интернет | публичный адрес | UDP 51820 | WireGuard (без валидного ключа молчит) |
| интернет | админка, API, БД, порты приложений, SSH | любые | **закрыто** (firewall + привязка nginx + проверка приложением) |
| устройство VPN | 10.77.0.1 | 443, 22, DNS | админка, SSH, split-DNS |
| устройство VPN | БД | 5432 | **закрыто даже из VPN** |
| `bb-site` | `bb-api` | 3101 loopback | секрет сайта |
| `bb-admin` | `bb-site` (обновление кеша новостей) | 3000 loopback | `REVALIDATE_TOKEN` |
| `bb-api`, `bb-admin` | PostgreSQL | 5432 loopback | роли `bb_api`, `bb_admin` |
| `bb-admin` | Telegram | исходящий | токен только у админки |
| pgBackRest | внешние хранилища КЗ | исходящий | шифрованные копии |

Публичного API-хоста нет: `bb-api` слышит только loopback. Это уменьшает видимую снаружи поверхность до одного сайта.

## 2. Слои защиты (каждый слой работает, даже если соседний ошибся)

| # | Слой | Что делает | Где |
|---|---|---|---|
| 1 | **Сеть и firewall** | политика drop; открыты UDP 51820, 80/443 на публичном интерфейсе, 22/443/DNS только из подсети VPN; 5432 и порты приложений не открыты нигде | `deploy/kz/nftables/` |
| 2 | **Привязка nginx** | админский хост слушает **только адрес VPN**; публичный листенер на чужое имя разрывает рукопожатие | `deploy/kz/nginx/` |
| 3 | **nginx `allow/deny`** | дополнительно только 10.77.0.0/24 | `admin.conf.template` |
| 4 | **Проверка в приложении** | процесс `admin` отвечает только на свой Host и только на запросы из сетей VPN (`X-Real-IP` пишет только nginx); чужие получают пустой 404; процесс `api` не содержит `/login` и админских маршрутов. Проверка выполняется на **каждый** запрос и на статику; **ни один заголовок клиента** (`next-router-prefetch` и др.) её не отключает | `platform/src/server/exposure.ts`, `proxy.ts` |
| 5 | **Fail closed** | профиль `PLATFORM_PROFILE=kz-production`: при неполной или неверной конфигурации процесс отвечает 503 на всё | `exposure.ts` |

| 7 | **Доказательство второго фактора в сессии** | сессия принимается только если **она сама** прошла второй фактор (`mfa_verified_at`); сессии, выданные раньше, отвергаются даже у тех, кто с тех пор включил MFA; принудительный отзыв старых сессий | `core/session.ts`, `scripts/revoke-sessions.ts` |
| 8 | **RBAC** | без изменений: Owner / Manager / Editor, проверка на сервере; внутри VPN права те же | `core/rbac.ts`, `dal.ts` |
| 9 | **Роли БД** | `bb_admin`: данные приложения, без DDL и TRUNCATE. `bb_api`: **нет прав ни на одну таблицу с ПДн** (контакты, заявки, согласия, очередь, аудит) **и ни на одну последовательность** (счётчики не тянет, не читает и не меняет: все записи идут внутри функций от имени владельца); читает только публичные неперсональные данные (с фильтром строк: только опубликованное) и исполняет девять узких функций `bb.intake_*`: каждая возвращает одну строку без имени и телефона, а **согласие записывается только в то обращение или регистрацию, которое принадлежит этому контакту и создано только что** | `scripts/db-roles.ts`, миграция 012 |
| 10 | **Секреты по процессам** | у каждого процесса только свои (раздел 8); профиль не запускает процесс с чужими | `exposure.ts`, `env/*.example` |
| 11 | **Cookie и сессии** | `__Host-`, HttpOnly, SameSite=Lax, Path=/, **без Domain**: принадлежит хосту админки; публичный сайт её не видит и не ставит; 12 ч простоя / 7 дней | `server/env.ts` |
| 12 | **CSRF, Origin, Host** | Server Actions сверяют Origin и Host; выгрузка отклоняет чужой Origin; чужой `Host` и `X-Forwarded-Host` дают 421 | `proxy.ts`, e2e |
| 13 | **Fail closed на запись заявок** | профиль сайта `SITE_PROFILE=kz-production`: `/api/lead` и `/api/consent` отвечают 503 и ничего не читают, пока `LEAD_PIPELINE` не равен точно `strict`, у сайта есть учётные данные Telegram, платформа не на loopback и т. п.; профиль админки требует `TELEGRAM_NOTIFY_LEVEL=minimal` (и в коде уровень принудительно `minimal`) | `src/lib/site-profile.ts`, `exposure.ts` |

## 3. Требования к VPS: 4 vCPU / 8 ГБ RAM, один сервер

- ЦОД в РК, договор с провайдером из РК (поручение обработки решает юрист, см. `PRODUCTION-PLAN-KZ.md`).
- Debian 12 / Ubuntu 24.04 LTS, ядро ≥ 5.6, `nftables`, `nginx` ≥ 1.25, PostgreSQL 16, Node.js 24 LTS, `pgbackrest`, `dnsmasq`, `chrony` (от времени зависят коды TOTP), `curl`.
- Публичный IPv4 (IPv6 по желанию), открытый **UDP**-порт, **консоль провайдера вне сети** (аварийная дверь), 2FA панели, снимки диска.
- Диски: системный SSD 60 ГБ + отдельный том PostgreSQL 40 ГБ (WAL); отдельное **внешнее** хранилище бэкапов.
- Сборка приложений **не на этом сервере**: готовые сборки (`next build`) собираются на машине разработки или в CI и копируются в `/opt/boombala/{site,platform}`; на сервере остаются только рантайм и зависимости.

**Бюджет памяти (8 ГБ):**

| Компонент | Память |
|---|---|
| PostgreSQL (`shared_buffers` ~1.5 ГБ + рабочая память) | ~2.5 ГБ |
| `bb-site` | до 1 ГБ (`MemoryMax=1G`) |
| `bb-api` | до 768 МБ |
| `bb-admin` | до 1 ГБ |
| nginx, WireGuard, dnsmasq, pgBackRest (во время копирования) | ~0.5 ГБ |
| ОС и кеш файлов | ~2 ГБ |

Нагрузка Boom Bala мала; запас хватает. Ограничение: единая точка отказа (один сервер), поэтому внешние копии и тренировка восстановления обязательны (раздел 6). Конкретные провайдеры и цены не оценивались: нужны коммерческие предложения.

## 4. Домен, TLS, DNS

- **Админка:** нейтральный домен (без слов Boom Bala, «admin», «panel»), регистратор с 2FA, скрытием WHOIS, отдельной учётной записью. **Публичной DNS-записи не создаётся.** Имя разрешается только внутри VPN через `dnsmasq` на 10.77.0.1 (`deploy/kz/dns/`). Сертификат: **ACME DNS-01** (временная TXT-запись через API регистратора; порт 80 для админки не нужен). Домен выбирается позже; в шаблонах `@ADMIN_HOST@`.
- **Публичный сайт:** сертификат по HTTP-01 (порт 80 на публичном адресе только для проверки и редиректа).
- Никаких wildcard-сертификатов и доменов, общих у сайта и админки.

**Переход публичного сайта с Vercel на КЗ-сервер (план, не выполнен).** DNS домена сайта меняется только по вашему отдельному подтверждению: заранее снизить TTL, поднять сайт на сервере и проверить по прямому адресу, затем переключить DNS. Vercel остаётся тестовым Preview и местом **откатного развёртывания в безопасном режиме** (см. ниже). Форма на КЗ-сайте работает только в режиме `strict` (раздел 2, слой 13).

**Безопасный сценарий отката DNS (возврат на Vercel не включает передачу ПДн).** Нынешний Production-проект на Vercel работает в режиме `telegram-only` и держит учётные данные Telegram: простой возврат DNS на него снова отправил бы имена и телефоны через Vercel и Telegram. **Поэтому DNS откатывается только на отдельное «откатное» развёртывание**, а не на старый Production:
1. *До переключения DNS (по вашему отдельному подтверждению):* создать отдельный проект/развёртывание на Vercel из кода релиза с окружением `deploy/kz/env/rollback.env.example` (`SITE_PROFILE=rollback-safe`): страницы работают, формы **всегда** отвечают «временно недоступно» (остаются телефон и WhatsApp); в проекте **нет** учётных данных Telegram и адреса платформы. Проверить: страницы открываются, `/api/lead` и `/api/consent` отвечают 503, в окружении нет `TELEGRAM_*` и `PLATFORM_*`. Этот профиль проверяется тестами и e2e даже в худшем случае (в окружение скопированы старые переменные Telegram).
2. *После устойчивой работы КЗ-сайта:* ротировать (отозвать) токен Telegram-бота, который использовал старый Production, и удалить `TELEGRAM_*` из старого проекта (действия владельца): даже ошибочное обращение DNS или алиаса к старому проекту больше не отправит заявку.
3. *Откат при отказе КЗ-сервера:* DNS возвращается **на откатное развёртывание** (не на старый Production). Посетитель видит сайт, а на месте формы сообщение и контакты; ПДн не проходят ни через Vercel, ни через Telegram.
4. *Если нужно продолжать принимать заявки во время отката:* только по телефону и WhatsApp (данные не попадают в наши системы). Возврат прежнего потока «форма → Telegram» это осознанное юридическое решение владельца, отдельное и по умолчанию запрещённое.
5. *Запрещено:* возвращать DNS на старый Production-проект, пока в нём есть `TELEGRAM_*` или режим `telegram-only`.

## 5. Доступ сотрудников: телефоны и компьютеры

Принципы: **одно устройство = один ключ = один адрес `/32`**; приватный ключ создаётся приложением WireGuard **на устройстве**; split tunnel (в VPN идёт только трафик к серверу); у каждого устройства свой preshared key.

**Подключение нового сотрудника**
1. Owner создаёт учётную запись (Сотрудники → роль, временный пароль ≥ 12 символов).
2. Сотрудник ставит WireGuard (iOS, Android, macOS, Windows, Linux), создаёт «пустой» туннель и передаёт администратору **публичный** ключ.
3. Администратор: `wg-staff.sh add --name "…" --email … --role … --pubkey …`. Конфигурацию (без приватного ключа) передают лично или через защищённый мессенджер и удаляют.
4. Сотрудник включает туннель, открывает адрес админки, входит: пароль, затем **включение второго фактора** (ключ или ссылка `otpauth://`), сохраняет 10 кодов восстановления отдельно от телефона.
5. Телефон и компьютер: два разных устройства (два ключа).

Нет VPN: админки нет (это сознательно); срочные действия только через сервер (раздел 7).

## 6. Резервные копии и восстановление (внешние)

- **pgBackRest**: архивация WAL (PITR) и копии, шифрование AES-256 на стороне клиента. **Две независимые внешние копии в КЗ:** repo1 (S3-совместимое хранилище другого ЦОД) и repo2 (второй хост по SFTP). Копия на том же диске резервной копией не считается (проверяется тестом).
- **Важно:** команда `pgbackrest backup` без `--repo` пишет **только в repo1**; repo2 тогда получал бы лишь WAL, но не копии. Поэтому есть **четыре отдельных задания**, каждое для одного хранилища и одного типа (`bb-backup-full-1/-2`, `bb-backup-diff-1/-2`; полные по воскресеньям, дифференциальные по будням; repo2 со сдвигом 1,5 ч). Скрипт `bb-backup.sh` принимает только `full-1|diff-1|full-2|diff-2`.
- **Ежедневная проверка обоих хранилищ** (`check-backups.sh`, таймер 07:00, при сбое алерт в операционный канал без ПДн). Для **каждого** хранилища отдельно: стенза в порядке; есть копия не старше 30 ч; есть полная копия не старше 8 дней; WAL-архив не пуст; `pgbackrest verify` проходит. Проблема только в одном хранилище тоже даёт отказ и называет его.
- **Тренировка восстановления** (`restore-drill.sh`, ежемесячно на отдельном чистом сервере): восстановление **из каждого хранилища** в свой пустой каталог (`repo1`, `repo2`); отказ при непустой цели и если одна из копий не восстановилась или результат без `PG_VERSION`; затем `backup-restore-check.mjs` (строки, миграции, индекс двойного бронирования, триггеры, RLS) на каждой восстановленной копии.
- Парольная фраза шифрования и ключи доступа хранятся отдельно от сервера (офлайн у владельца); фраза общая для двух хранилищ, её потеря означает потерю обеих копий.
- Срок хранения копий = предел полного удаления данных (вопрос юристу). После восстановления из копии **обезличивание нужно применить заново** по списку `contact.anonymized` из журнала аудита.

## 7. Отзыв доступа и восстановление владельца

**Увольнение (порядок):** (0) `wg-staff.sh revoke --email …`: устройства теряют путь сразу, и пир не вернётся после перезагрузки; (1) в админке «Отключить» (сессии завершаются); (2) просмотр журнала; (3) при необходимости ротация общих секретов и паролей хостинга; (4) запись в журнале персонала.
**Потерян телефон:** отозвать это устройство (`--id`), Owner «Сбросить второй фактор», новое устройство.

**Восстановление владельца, слои:**
1. 10 одноразовых кодов восстановления (на бумаге, отдельно от телефона).
2. Второй Owner (заместитель) со своими устройствами.
3. Консоль провайдера вне сети (не зависит от VPN, защищена 2FA панели): `npm run user:mfa-reset -- --email …`, `npm run user:set-password -- --email …`, `npm run sessions:revoke -- --all`, `wg-staff.sh add …`. Каждое действие в аудите как «консоль сервера».
4. Организационно: кто имеет доступ к панели провайдера, запечатанная процедура. **Администратор сервера с root технически видит БД**: это вопрос доверия и договора.

## 11. Остаточные риски и решения

1. **TOTP** уязвим к фишингу в реальном времени; VPN, проверка Host и сети снижают риск. WebAuthn отложен.
2. **Один VPS:** единая точка отказа и общий блок последствий при взломе ОС. Смягчают раздельные пользователи, роли БД, внешние копии; вариант двух серверов остаётся опцией на будущее.
3. **VPN как единая точка:** без VPN админки нет; аварийный путь только консоль провайдера.
4. **Администратор сервера** с root видит БД и секреты: договор и минимум людей.
5. **Оракул существования:** процесс `bb_api` может узнать, существует ли точная пара (имя, телефон) (возвращается id), но не прочитать данные и не перечислить контакты (покрыто тестом).
6. Юридические вопросы из `PRODUCTION-PLAN-KZ.md` техника не решает.

## 12. Порядок применения (когда будут сервер и домены)

1. Хостинг: 2FA панели, консоль вне сети, снимки; обновления, `chrony`, пользователи `bbsite`, `bbapi`, `bbadmin`.
2. `render.sh` с `deploy.env`; `nftables`; WireGuard (`wg genkey` на сервере в `/etc/wireguard/server.key`, 0600); `wg-quick@wg0`, `bb-vpn-peers.service`.
3. PostgreSQL: конфиг и `pg_hba`; БД и `bb_owner`; `npm run db:migrate` (001…012) под `bb_owner`; `npm run db:roles` (создаёт `bb_api`, `bb_admin`, права и политики); `npm run db:seed`; Owner (`user:create`).
4. Приложения: готовые сборки сайта и платформы; `site.env`, `api.env`, `admin.env` из примеров (секреты генерируются на сервере); `bb-site`, `bb-api`, `bb-admin`, `bb-outbox.timer`.
5. nginx: сайт на публичном адресе; админка на адресе VPN; сертификаты; `dnsmasq`.
6. Резервные копии: `pgbackrest.conf`, stanza, первая полная копия, **тренировка восстановления**.
7. Проверки: `verify-isolation.sh` снаружи и изнутри VPN; тесты роли БД и MFA на этом сервере; пробный вход Owner с MFA; тренировка отзыва устройства и аварийного входа.
8. Только после этого и после юридических решений обсуждается DNS-переход сайта и включение приёма данных.
