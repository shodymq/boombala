# Изоляция админки: отдельный домен, VPN, MFA, роли БД

Статус: **подготовка архитектуры, конфигураций и тестов в `release/preview`.** Ничего не развёрнуто: Production, `main`, DNS, реальные данные и флаги сбора ПДн не менялись, домен и сервер не покупались, настоящих адресов в репозитории нет (только примеры `example.test`, `10.77.0.0/24`, `198.51.100.10`).

Решение владельца: админка **не** на домене публичного сайта: ни на нём самом, ни на его поддомене, ни по пути вида `/admin`. Она работает отдельным приложением на отдельном нейтральном домене (выбирается и покупается позже), доступном только через собственный WireGuard-VPN в Казахстане.

## 1. Схема подключения

```
 ИНТЕРНЕТ                                            СЕРВЕР(Ы) В КАЗАХСТАНЕ
 ─────────                                           ───────────────────────────────────────────────────────────
 Посетитель ──► boombala.kz (Vercel, только контент; ни одного маршрута админки, ни одной cookie сотрудников)
     │
     │  (сайт вызывает API сервер-в-сервер по секрету; позже: форма из браузера напрямую)
     ▼
 api.boombala.kz :443  ──►  nginx (публичный адрес) ──► bb-api  127.0.0.1:3101   роль PLATFORM_ROLE=api
                              только /api/health, /api/public/*, /api/intake/*;         БД-роль bb_api (вставка и чтение)
                              лимиты, тело ≤ 8 КБ, всё остальное 404                    ─────────────┐
                                                                                                     ▼
 Сотрудник ─ WireGuard UDP 51820 ─► wg0 10.77.0.1 ─► nginx (адрес VPN, НЕ публичный) ─► bb-admin 127.0.0.1:3100   ──► PostgreSQL
 (телефон / компьютер,                                  <ADMIN_DOMAIN> :443                роль PLATFORM_ROLE=admin    127.0.0.1:5432
  одно устройство = один ключ)                          allow 10.77.0.0/24; deny all       БД-роль bb_admin            (только изнутри)
                                                                                           MFA обязателен
 Таймер systemd (loopback) ─► bb-admin /api/cron/outbox ─► Telegram (уведомления, только из этого процесса)
```

| Откуда | Куда | Порт | Разрешено |
|---|---|---|---|
| интернет | публичный адрес | 443 (и 80 для редиректа/ACME) | только API-хост |
| интернет | публичный адрес | UDP 51820 | WireGuard (рукопожатие без валидного ключа молчит) |
| интернет | админка, БД, порты приложений, SSH | любые | **закрыто** (firewall + привязка nginx + проверка приложением) |
| устройство VPN | 10.77.0.1 | 443, 22, DNS | админка, SSH, split-DNS |
| устройство VPN | БД | 5432 | **закрыто даже из VPN** |
| устройство VPN | интернет через сервер | любой | нет (split tunnel, форвардинга нет) |
| `bb-api` | PostgreSQL | 5432 loopback (или приватная сеть) | роль `bb_api` |
| `bb-admin` | PostgreSQL, Telegram, публичный сайт (revalidate) | исходящие | роль `bb_admin` |

## 2. Слои защиты (каждый слой работает, даже если соседний ошибся)

| # | Слой | Что делает | Где |
|---|---|---|---|
| 1 | **Сеть и firewall** | политика drop; открыты UDP 51820, 80/443 на публичном интерфейсе, 22/443/DNS только из подсети VPN; 5432 и порты приложений не открыты нигде | `deploy/kz/nftables/` |
| 2 | **Привязка nginx** | админский виртуальный хост слушает **только адрес VPN**; публичный листенер отвечает на чужое имя разрывом рукопожатия; нет порта 80 для админки | `deploy/kz/nginx/` |
| 3 | **nginx `allow/deny`** | дополнительно только 10.77.0.0/24 | `admin.conf.template` |
| 4 | **Проверка в приложении** | процесс `admin` отвечает только на свой Host и только на запросы с адресов VPN (заголовок `X-Real-IP` пишет только nginx); чужие получают пустой 404 без редиректа на логин; процесс `api` вообще не содержит `/login` и админских маршрутов | `platform/src/server/exposure.ts`, `proxy.ts` |
| 5 | **Fail closed** | профиль `PLATFORM_PROFILE=kz-production`: при неполной или неверной конфигурации (нет MFA, нет списка сетей, чужие секреты) процесс отвечает 503 на всё | `exposure.ts` |
| 6 | **Аутентификация** | пароль (argon2id) **и** TOTP (RFC 6238) у Owner, Manager и Editor; пароль без кода даёт только «ожидающую» сессию, которую админка не принимает; код работает один раз; неверные коды считаются в общем лимите попыток | `core/auth.ts`, `core/mfa.ts`, `core/totp.ts` |
| 7 | **RBAC** | без изменений: Owner / Manager / Editor, проверка на сервере в каждом действии; внутри VPN права те же | `core/rbac.ts`, `dal.ts` |
| 8 | **Роли БД** | `bb_api`: вставка заявок и согласий, чтение публичного; нет доступа к сотрудникам, сессиям, MFA, журналу выгрузок, настройкам retention, чтению аудита и очереди. `bb_admin`: данные приложения, без DDL и TRUNCATE; триггеры истории продолжают защищать | `platform/scripts/db-roles.ts` |
| 9 | **Секреты по приложениям** | у каждого процесса только свои (см. раздел 8); профиль отказывается стартовать с чужими | `exposure.ts`, `env/*.example` |
| 10 | **Cookie и сессии** | cookie сессии с префиксом `__Host-`, HttpOnly, SameSite=Lax, Path=/, **без Domain**: принадлежит только хосту админки; публичный сайт её не видит и не ставит; сессия 12 ч простоя / 7 дней | `server/env.ts`, `login/actions.ts` |
| 11 | **CSRF, Origin, Host** | Server Actions Next.js сверяют Origin и Host; выгрузка отклоняет чужой Origin; чужой `Host` и подмена `X-Forwarded-Host` дают 421 | `proxy.ts`, e2e |

## 3. Требования к VPS в Казахстане

**Общие (оба варианта)**
- Расположение: ЦОД в РК, договор с провайдером из РК (вопрос о поручении обработки решает юрист, см. `PRODUCTION-PLAN-KZ.md`).
- ОС: Debian 12 / Ubuntu 24.04 LTS, ядро ≥ 5.6 (WireGuard в ядре), `nftables`, `nginx` ≥ 1.25 (`http2 on`, `ssl_reject_handshake`), PostgreSQL 16, Node.js 24 LTS, `curl`, `dnsmasq`.
- Публичный IPv4 (IPv6 по желанию); возможность открыть **UDP** порт; **консоль провайдера вне сети** (VNC/serial): это «аварийная дверь», если VPN недоступен.
- Панель провайдера с обязательной 2FA, отдельная учётная запись владельца, снимки диска (snapshots), возможность приватной сети между серверами.
- Синхронизация времени (chrony): от неё зависят коды TOTP.
- Диски: системный SSD + отдельный том под PostgreSQL (WAL), запас ×3 от оценки данных; отдельное хранилище бэкапов в другом ЦОД КЗ.
- Без управляющих панелей (cPanel/Plesk), без публичного SSH-порта.

**Вариант 1: один VPS (пилот).** 2 vCPU, 4 ГБ RAM, 40–60 ГБ SSD (+ том БД 20 ГБ). На нём всё: nginx, bb-api, bb-admin, PostgreSQL, WireGuard. Минус: компрометация публичного API ближе к БД и админке.
**Вариант 2: два сервера (рекомендуется для Production).**
- Узел «edge»: nginx публичный + `bb-api`, 1–2 vCPU, 2 ГБ RAM. Подключается к БД по **приватной сети** ролью `bb_api`.
- Узел «core»: PostgreSQL + `bb-admin` + WireGuard + nginx админки, 2 vCPU, 4–8 ГБ RAM, SSD с запасом под WAL. Публичных портов, кроме UDP 51820, нет.
- Приватная сеть между узлами; `pg_hba.conf` пускает `bb_api` только с адреса edge; БД слушает приватный адрес, не публичный.

Расходы и конкретные провайдеры в документе не оцениваются: нужны коммерческие предложения.

## 4. Домен и TLS админки

- Домен выбирается и покупается позже, **нейтральный** (без слов Boom Bala, бренда, «admin», «panel»). Регистратор с 2FA, скрытием данных WHOIS, отдельной учётной записью.
- **Публичной DNS-записи для домена админки не создаётся.** Имя разрешается только внутри VPN через `dnsmasq` на 10.77.0.1 (split-DNS, `deploy/kz/dns/`). Проверка: `dig +short <ADMIN_DOMAIN>` из интернета пуст (проверяет `verify-isolation.sh`).
- Сертификат: **ACME DNS-01** (временная TXT-запись у регистратора, нужен API-токен регистратора) либо собственный УЦ (например, `step-ca`) с установкой корня на устройства сотрудников. Порт 80 для админки не открывается.
- Никаких wildcard-сертификатов и wildcard-доменов, общих с публичным сайтом.
- Подробности о выбранном домене: **не придумываются**; в шаблонах `@ADMIN_HOST@`.

## 5. Доступ сотрудников: телефоны и компьютеры

Принципы: **одно устройство = один ключ = один адрес `/32`**; приватный ключ создаётся приложением WireGuard **на устройстве** и сервер его не видит; split tunnel (в VPN идёт только трафик к серверу, обычный интернет телефона не затрагивается); у каждого устройства свой preshared key.

**Подключение нового сотрудника**
1. Owner создаёт учётную запись в админке (Сотрудники → роль, временный пароль ≥ 12 символов).
2. Сотрудник ставит приложение WireGuard (iOS, Android, macOS, Windows, Linux), создаёт туннель «пустой» и копирует **публичный** ключ администратору.
3. Администратор сервера: `wg-staff.sh add --name "…" --email … --role … --pubkey …` (скрипт выбирает адрес, создаёт PSK, применяет пир, пишет реестр). Конфигурацию (без приватного ключа) передают лично или через защищённый мессенджер и затем удаляют.
4. Сотрудник включает туннель, открывает адрес админки в браузере, входит: пароль, затем **включение второго фактора** (ключ или ссылка `otpauth://` в приложение-аутентификатор), сохраняет 10 кодов восстановления отдельно от телефона.
5. Для телефона и компьютера выдаются **разные** устройства (два ключа).

**Нет VPN или потеряно устройство.** VPN недоступен — админка недоступна; это сознательно. Срочные действия вне админки возможны только через сервер (см. раздел 7).

## 6. Отзыв доступа уволенному сотруднику (порядок и сроки)

| Шаг | Действие | Эффект |
|---|---|---|
| 0 (минута 0) | `wg-staff.sh revoke --email <почта>` | все устройства теряют сетевой путь сразу; пир удалён и **не вернётся** после перезагрузки (реестр помечен) |
| 1 | Админка: Сотрудники → «Отключить» (или Owner меняет пароль) | учётная запись неактивна, сессии завершены |
| 2 | Проверка журнала: последние входы и действия сотрудника | оценка |
| 3 | Если у человека были общие секреты (не должны быть) или доступ к серверу: ротация (`DATABASE_URL`, `CRON_SECRET`, токены), смена паролей хостинга | закрытие остаточного риска |
| 4 | Фиксация в журнале персонала | порядок |

Потерян телефон: сразу пункт 0 для этого устройства (`--id`), затем Owner «Сбросить второй фактор» (сессии завершатся), сотрудник заново включает MFA на новом устройстве.

## 7. Восстановление доступа владельца

Слои, от простого к аварийному:
1. **Коды восстановления** (10 одноразовых, показываются при включении MFA): хранить на бумаге отдельно от телефона (сейф, запечатанный конверт). Каждый используется один раз.
2. **Второй Owner (заместитель)**: со своими устройствами и кодами; он может «Сбросить второй фактор» у первого. Система защищает от остатка без владельца, но не требует двух: рекомендовано завести.
3. **Консоль сервера (аварийный доступ)**: через консоль провайдера вне сети (она не зависит от VPN, защищена 2FA панели) администратор запускает:
   - `npm run user:mfa-reset -- --email <owner>`: снимает второй фактор и завершает сессии;
   - `npm run user:set-password -- --email <owner>`: задаёт новый пароль (скрытый ввод) и завершает сессии;
   - `wg-staff.sh add …`: новое VPN-устройство.
   Каждое действие пишется в журнал аудита как «консоль сервера».
4. **Организационное**: список, кто имеет доступ к панели провайдера (2FA, минимум людей), кто доверенный администратор; процедура хранится запечатанной у юриста/владельца. **Администратор сервера с root технически видит БД**: это вопрос доверия и договора, а не кода.

**Не сделано (план)**
1. **Публичный приём из браузера напрямую** на `api.`: эндпоинт без секрета, CORS по одному Origin, лимиты на уровне приложения, bot-защита без сторонних сервисов, идемпотентность (сегодня приём требует секрета сайта, т. е. идёт через Vercel).
2. Переменные Vercel: завести `REVALIDATE_TOKEN`, убрать общий токен; убрать зависимость `@vercel/oidc` в Production.
3. WebAuthn/ключи доступа как более сильный второй фактор (TOTP уязвим для фишинга; VPN и Host-проверки снижают риск, но не убирают).
4. Скрипт повторного применения обезличиваний после восстановления из бэкапа; шифрованные бэкапы; отправка логов в защищённое хранилище.
5. Привязка сессии к устройству (по желанию), оповещение владельца о входе с нового устройства.
6. Автоматическая проверка (`nginx -t`, `nft -c`, `wg-quick strip`, `shellcheck`) в CI на образе с реальными бинарниками.

## 11. Остаточные риски и решения владельца

1. **TOTP vs WebAuthn.** TOTP даёт защиту от кражи пароля, но не от фишинга в реальном времени. Внутри VPN риск мал; WebAuthn стоит запланировать.
2. **Один VPS или два.** Вариант 2 заметно снижает последствия взлома публичного API.
3. **VPN как единая точка:** недоступен VPN, недоступна админка (аварийный доступ только через консоль провайдера).
4. **Администратор сервера**: root видит БД и секреты, нужен договор и минимум людей.
5. **`bb_api` читает таблицу контактов** (нужно для upsert заявки): компрометация API-процесса раскрывает контакты. Снижение: перенести приём в функции `SECURITY DEFINER` (в плане).
6. **Выбор домена и регистратора** (нейтральный, 2FA, отдельный аккаунт) и способ сертификата (DNS-01 или свой УЦ).
7. Юридические вопросы из `PRODUCTION-PLAN-KZ.md` (локализация, поручение обработки, роль администратора) по-прежнему не решены техникой.

## 12. Порядок применения (когда будет сервер и домен)

1. Хостинг: 2FA панели, консоль вне сети, снимки; обновления, `chrony`, пользователи `bbadmin`, `bbapi`, отдельный `postgres`.
2. `render.sh` с `deploy.env` (адреса, порты, домены); `nftables`; WireGuard (`wg genkey` на сервере в `/etc/wireguard/server.key`, права 0600); `wg-quick@wg0`, `bb-vpn-peers.service`.
3. PostgreSQL: `postgresql.conf`, `pg_hba.conf`; создать БД и `bb_owner`; `npm run db:migrate` (001…010) под `bb_owner`; `npm run db:roles` (`bb_api`, `bb_admin`); `npm run db:seed`; создать Owner (`user:create`).
4. Приложения: сборка `platform` на сервере; файлы `/etc/boombala/admin.env` и `api.env` из примеров (секреты генерируются на сервере и никуда не копируются); `bb-admin`, `bb-api`, `bb-outbox.timer`.
5. nginx: API-хост на публичном адресе; админка на адресе VPN; сертификаты; `dnsmasq` (split-DNS).
6. Проверка: `verify-isolation.sh` из внешней сети и из VPN; тесты роли БД и MFA на этом сервере; пробный вход Owner с включением MFA; тренировка отзыва устройства и аварийного входа.
7. Только после этого и после юридических решений обсуждается включение приёма данных.
