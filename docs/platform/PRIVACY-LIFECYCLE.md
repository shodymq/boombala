# Отзыв согласия, обезличивание и хранение данных

Статус: реализована **основа**. Автоматическое удаление **выключено** и по расписанию не запускается нигде.
Юридические документы (V3.3), `/privacy` и тексты согласий этой работой не затронуты.

## 1. Зависимости данных

```
contacts ◄── consent_registrations (QR-регистрация)           контакт = имя + телефон (может быть пустым только у QR)
        ◄── consent_events (история согласий, append-only)    contact_id, document_id (версия), event, ip_hash, user_agent
        ◄── lead_requests (заявка на день рождения)           status new|in_progress|confirmed|cancelled|completed
        ◄── slot_reservations (бронь/блок, без удаления)      contact_id, снимок цены; активная бронь держит слот
lead_requests ◄── consent_events, slot_reservations
```

Один контакт может быть и QR, и заявкой, и бронью (один номер и то же имя). Поэтому «прошло 12 месяцев с QR» **не** значит «можно удалить контакт».

## 2. Что значит «удалить»
Строки **не удаляются**: на контакт ссылаются история согласий (удалять нельзя по дизайну), заявки и брони. Контакт **обезличивается**:
- `name` → «Анонимизировано», `name_key` → `anon:<id>`, `phone_e164` → `NULL`, `marketing_opt_in` → `false`, `anonymized_at` = момент;
- в `consent_events` стираются только косвенные идентификаторы: `ip_hash` и `user_agent`. История (кто, какая версия документа, когда, как) остаётся;
- обезличенный контакт не восстанавливается (триггер); новая регистрация с тем же номером создаёт **новый** контакт.

## 3. Правила: когда можно
`assessContact` считает «блокеры» (одно место в `platform/src/core/privacy.ts`):

| Блокер | Смысл | Почему |
|---|---|---|
| `active_booking` | бронь держит слот | обязательство перед клиентом; БД тоже отказывает |
| `open_enquiry` | заявка new / in_progress / confirmed | обязательство; БД тоже отказывает |
| `booking_record` | любая бронь, в т.ч. отменённая и прошедшая | срок хранения **не решён** (юрист/бухгалтерия) |
| `enquiry_record` | любая заявка, в т.ч. закрытая | срок хранения **не решён** (юрист) |

Обезличить можно только контакт **без блокеров** и с отозванным согласием. Для двух последних блокеров правило не придумано: запись сохраняется и попадает в отчёт.
Практически сегодня обезличивается только контакт, у которого есть лишь QR-регистрации.

## 4. Отзыв согласия
`revokeConsent` (только Владелец, `privacy.manage`): добавляет `revoked` к каждому согласию на обработку данных, у которого последнее событие «дано» (`method='staff'`, `recorded_by`, `note` — код: `subject_request`, `retention_expired`, `legal_request`; свободный текст запрещён CHECK-ом), снимает `marketing_opt_in`. Повтор ничего не меняет. Сам по себе ничего не стирает: если есть блокер, отзыв записан, данные сохранены, в карточке указана причина.

## 5. Retention (12 месяцев)
Срок из `retention_settings.qr_months` (по умолчанию 12; согласован владельцем, правовая достаточность проверяется юристом), считается от **последней** QR-регистрации контакта.
- `retentionReport` / страница «Хранение данных» (**dry-run**, ничего не меняет): сколько контактов не истекло, сколько подлежит обработке, сколько **нельзя трогать** (и почему), вне правила. Только идентификаторы, без имён и телефонов.
- `runRetention({ dryRun: false })` выполняет обезличивание, только если `auto_enabled` **и** записано юридическое подтверждение (`legal_confirmed_at`). Иначе `RetentionDisabledError`. Это проверяется и в БД (`CHECK (NOT auto_enabled OR legal_confirmed_at IS NOT NULL)`).
- Нет ни маршрута, ни cron, ни задачи, которые вызывают `runRetention`: запуск возможен только явно, из кода. **Сейчас автоматическая обработка выключена.**
- Параметры: `updateRetentionSettings` (Владелец, с аудитом). Снятие подтверждения выключает автообработку.

## 6. Где остаются персональные и косвенно идентифицирующие данные

| Место | Что | Состояние |
|---|---|---|
| `consent_events.ip_hash`, `user_agent` | косвенные идентификаторы | стираются при обезличивании (разрешено только для обезличенного контакта) |
| `audit_log` | только id, коды, цены, даты; имён, телефонов, IP посетителей нет | чисто. Остаётся свободный текст сотрудника: `after.reason` при отмене брони |
| `slot_reservations.note`, `release_reason` | свободный текст сотрудника (до 300 символов) | **риск**: сотрудник может написать имя или телефон; удалить нельзя (брони неизменяемы). Нужна инструкция сотрудникам не писать туда личные данные |
| `export_log.filters` | раньше записывался сырой поиск `q` (имя/цифры телефона) | **исправлено**: теперь `"[redacted]"`. Старые строки в append-only таблице остаются (на `boombala-test` синтетика) |
| Выгрузки CSV/XLSX | имя, телефон, источник | обезличенные контакты выгружаются как «Анонимизировано» без телефона |
| Логи приложения | только коды и имена классов ошибок, id | персональных данных нет |
| Telegram | сообщение о заявке содержит имя и телефон (поток заявок не менялся) | **вне БД, платформа стереть не может**: срок хранения чата и допустимость решает юрист |
| Резервные копии | Supabase Free не даёт скачиваемых копий и PITR | при восстановлении из копии обезличенные контакты вернутся с данными. Список обезличенных восстанавливается из `audit_log` (`contact.anonymized`, `entity_id`) и применяется заново. До Production нужен платный план/процедура |
| Vercel/Supabase | зарубежный хостинг | вопрос локализации в РК не закрыт (блокер Production) |

## 8. Можно ли установить личность после обезличивания (оценка)

Проверено тестом: после обезличивания поиск по **всем** таблицам схемы не находит имя, телефон, IP-хеш и строку браузера посетителя.

Что остаётся у обезличенного QR-контакта:
- случайный `id` контакта (`uuid`), `anon:<id>` вместо ключа имени;
- время регистраций (`created_at`, `first_registered_at`, `last_activity_at`), порядковые номера регистраций (`seq`);
- события согласий: время, версия документа, способ, id сотрудника (для записи об отзыве);
- записи аудита: тот же `id`, время, id сотрудника.

Оценка: **по данным только этой БД личность не восстанавливается**. Остаточный риск косвенный:
1. **Время регистрации** можно сопоставить с внешними сведениями (видеонаблюдение, журнал входа, очередь у стойки): при малом потоке посетителей по времени можно выйти на человека. Огрубление времени не сделано: решение о необходимости и о способе принимает юрист, правила я не придумывал.
2. **Копии и выгрузки до обезличивания** содержат соответствие `id → имя/телефон`: любой CSV/XLSX, скриншот или резервная копия, сделанные раньше, снова дают личность. Выгрузки уходят за пределы системы и вернуть их нельзя.
3. **Telegram**: для заявок (не QR) имя и телефон остаются в сообщении чата.
4. Контакт, у которого есть заявка или бронь, **не обезличивается вообще**: у него остаются имя и телефон.
5. Свободный текст сотрудников (`note`, причины отмены) может содержать личные данные и не очищается.
