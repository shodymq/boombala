# Посещаемость: количество детей в QR-регистрации и учёт фактических входов

Миграция `013_attendance.sql`. Ничего из этого не включается в Production автоматически: приём данных остаётся выключенным
(`PII_INTAKE_ENABLED`, `CONSENT_FORM_ENABLED`), пока нет утверждённых документов и хранилища в Казахстане.

## Правило, ради которого всё сделано

**QR-регистрация — это заявление взрослого, а не посещение.** В статистику «детей вошло» попадают только записи о входе
(`attendance_entries`), которые создал сотрудник: подтвердил QR-регистрацию или внёс вход вручную. Ожидаемые дети
(по регистрациям без подтверждения) показываются отдельно и никогда не складываются с фактическими.

## Что собирается

- В QR-форме: имя взрослого, телефон (необязательно), **количество детей 1–50**, два отдельных подтверждения документов.
- Ни ФИО, ни ИИН, ни даты рождения детей нигде не запрашиваются и не хранятся: в схеме нет для них колонок
  (проверяется тестом по списку колонок), лишние поля запроса отбрасываются.
- Старые регистрации (до 013) остаются с `children_count = NULL`: число не выдумывается; сотрудник указывает фактическое число при подтверждении.

## Путь значения

сайт (счётчик − / +, старт 1) → `/api/consent` (целое 1–50, иначе 400) → платформа `/api/intake/consent` (zod, 1–50) →
`bb.intake_insert_registration(key, contact, children)` (`SECURITY DEFINER`; `CHECK` 1–50 в таблице; двухаргументной версии больше нет) →
`consent_registrations.children_count`. Повтор того же ключа возвращает первую регистрацию, число первого запроса сохраняется.

## Записи о входе

`attendance_entries`: количество детей (1–50 при создании), момент входа, **день по `Asia/Almaty` считает база**
(`entry_date`, генерируемая колонка), способ (`qr` с регистрацией / `manual` без), кто подтвердил, ключ идемпотентности.

- **Защита от повтора:** один вход на регистрацию (уникальный индекс), у ручного входа — ключ идемпотентности формы.
  Двойное нажатие, сетевой повтор и два сотрудника одновременно дают одну запись, цифра растёт один раз.
- **Исправления:** `children_count` можно менять (0 отменяет вход), но только через `correctEntry`: он блокирует строку,
  сверяет число, которое сотрудник видел на экране (устаревший экран получает отказ, а не молча перезаписывает), и задаёт
  в транзакции автора и причину. **Журнал `attendance_corrections` пишет сама база триггером** при любом изменении числа
  (было, стало, причина-код, кто, когда); любое другое изменение записи, `DELETE` и `TRUNCATE` запрещены. Причины — коды, не свободный текст.
- **Аудит:** `attendance.confirmed`, `attendance.manual`, `attendance.corrected` в `audit_log`.
- **Права:** новое право `attendance.manage` — Owner и Manager; у Editor нет (ни раздела, ни карточки на обзоре, `/attendance` перенаправляет).
  `bb_api` не имеет доступа к таблицам; `bb_admin` читает и пишет, но не удаляет и не делает DDL.

## Цифры в админке

- «Детей вошло» = сумма `children_count` записей с `entry_date` = выбранный день.
- «Взрослых прошло QR-регистрацию» = регистрации, созданные в этот день по Алматы.
- «Детей ожидается» = заявленные дети регистраций этого дня, у которых нет подтверждённого входа.
- Таблица и график — по дням (14 или 30), дни без данных показываются с нулями.
- Фраза вида «24 октября вошло 500 детей» появляется только если сумма подтверждённых входов этого дня равна 500
  (проверено тестом: 500 заявленных детей без подтверждений дают «ожидается 500, вошло 0»).

## Что нужно на сервере в Казахстане

1. Применить миграцию 013 штатным мигратором под `bb_owner` (`npm run db:migrate`) и **повторить `npm run db:roles`**: старая функция
   `intake_insert_registration(uuid, uuid)` заменена трёхаргументной, право `EXECUTE` выдаётся заново.
2. Развернуть платформу и сайт вместе с PostgreSQL в КЗ (план `PRODUCTION-PLAN-KZ.md`); `PII_INTAKE_ENABLED=1` и `CONSENT_FORM_ENABLED=1` — только после утверждения документов владельцем.
3. Опубликовать утверждённые документы (`visit_rules`, при необходимости `companion_duties`, `personal_data_consent`); форма берёт тексты и редакции из платформы.
4. Создать сотрудников (Owner, Manager) с TOTP; Manager получает «Посещаемость» автоматически.
5. Проверить на сервере: регистрация с 1/3/10 детьми, подтверждение входа, повтор нажатия, исправление, ручной вход, смена дня в полночь по Алматы; часы сервера и часовой пояс базы значения не имеют (день считает база по `Asia/Almaty`).
6. Резервная копия: таблицы входят в обычный `pgBackRest`; отдельных настроек нет.
