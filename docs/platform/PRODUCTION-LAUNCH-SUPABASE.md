# Production на Supabase: только синтетические данные до переноса в Казахстан

Решение владельца от 23 октября 2026: отдельная Production-база Supabase, перенос на VPS в Казахстане примерно через неделю. **Это решение не разрешает принимать реальные ПДн в Supabase (Франкфурт):** приём включается только после переноса хранения в Казахстан и утверждения документов. До этого в базе допустимы лишь синтетические помеченные данные.
Код QR-регистрации и посещаемости уже в `main` (PR #8, #10); в Production-проекте сайта пока нет ни одного флага, поэтому всё выключено.
Документ перечисляет этапы, точный набор переменных (только имена, значения не хранятся в репозитории) и то, что блокирует каждый этап.

## Переменные (имена; значения только в Vercel, тип Sensitive)
**boombala-platform (Production):** `DATABASE_URL` (роль `bb_admin`, пулер Supabase, порт 6543), `DATABASE_CA_CERT`, `PLATFORM_HTTPS=1`,
`PLATFORM_INTAKE_TOKEN`, `CRON_SECRET`, `PLATFORM_IP_PEPPER`, `SITE_REVALIDATE_URL`, `PII_INTAKE_ENABLED` (сначала не задана),
`MFA_MODE=required` и `MFA_ENC_KEY` (32 байта base64), `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_NOTIFY_LEVEL` (по решению владельца).
**boombala (Production, уже есть):** `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_MAP_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.
Добавить позже: `PLATFORM_URL`, `PLATFORM_INTAKE_TOKEN`, `LEAD_PIPELINE` (только после проверки; `dual` оставляет Telegram как запасной путь), затем флаги этапов 7 и 8.
Публичный API на роли `bb_api` (девять функций `intake_*`, без прав на таблицы), админка на роли `bb_admin` (без DDL и удаления).

## Порядок проверок перед включением приёма данных
1. `npm run preflight` против Production-базы: OK.
2. Права: `bb_api` не читает контакты, заявки, согласия, посещаемость, аудит; `bb_admin` не удаляет и не делает DDL (тесты `tests/db-roles.test.ts`, `tests/attendance.test.ts` и проверка на самой базе).
3. Документы опубликованы; `GET /api/public/legal` отдаёт версии; форма `/consent` показывает редакции.
4. Сквозной тест (этап 9) до открытия страницы публике; затем удаление синтетических строк по отслеженным ключам; подсчёт: контактов и регистраций с именами «ТЕСТ…» ноль.
5. Идемпотентность: повтор запроса с тем же ключом, двойное нажатие, два сотрудника одновременно (см. e2e `attendance`).
6. Telegram: одна заявка владельцу, согласованная заранее (реальное сообщение отправляется только с разрешения).

## Резервная копия и выгрузка для переноса на VPS
- План Free не даёт скачиваемых резервных копий и PITR: до перехода на Pro единственная защита — собственная логическая выгрузка. Для реальных данных нужен Pro.
- Выгрузка: `bb`-схема целиком (структура из миграций + данные), с контрольными суммами таблиц, проверка восстановления в пустую базу
  (`npm run backup:check`; для Supabase нужен `pg_dump` версии не ниже сервера и direct/session-строка подключения).
- Файлы выгрузки содержат персональные данные: хранить зашифрованными, не в репозитории.
- Для переезда на VPS: те же миграции 001–013 на пустой базе в КЗ, загрузка данных, `db:roles`, `preflight`, сверка контрольных сумм, переключение `DATABASE_URL`.
