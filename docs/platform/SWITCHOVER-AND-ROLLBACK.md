# Переключение CRM и QR: порядок, проверки, откат

**Состояние на 23.10.2026:** интерфейсы и сквозной синтетический E2E реализованы, но реальный приём ПДн выключен. Ни успешная сборка, ни публикация документов сами по себе не означают статус LIVE.

## 0. Обязательные условия
1. Владелец утверждает обе языковые редакции документов `visit_rules`, `personal_data_consent` и страницы `/privacy`; казахские тексты проверены компетентным специалистом. Утверждение в админке выполняет Owner, не скрипт без его согласия.
2. Подтверждены полные сведения ИП и реквизиты `LEGAL_OPERATOR_NAME`, `LEGAL_OPERATOR_IIN`, `LEGAL_OPERATOR_REG_ADDRESS`. Если любой реквизит не заполнен или ошибочен, `/privacy` показывает предупреждение о неполной редакции: **не активировать формы**.
3. База для ПДн и резервные копии размещены в Казахстане, реальный сетевой путь и трансграничные сервисы проверены с учётом применимых требований РК. Временное зарубежное хранилище Supabase (Франкфурт) для реальных QR/CRM-записей не использовать.
4. Подготовлены безопасные выходы в Telegram без персональных данных, подтверждены права сотрудников, восстановление резервных копий и работоспособность кассы/правил. До публикации изъять материалы с узнаваемыми детьми без разрешений на соответствующее использование.
5. На казахстанской базе применены миграции 001–013, разделение ролей, `npm run preflight`, `npm run verify:roles`. Затем под Owner публикуются **только одобренные** версии `visit_rules` и `personal_data_consent` (RU+KK в одной версии каждого типа).

## 1. Не путать временную схему с казахстанским Production

| Режим | Где применяется | Сайт | CRM/QR |
|---|---|---|---|
| Текущее размещение на Vercel + Supabase Frankfurt | Только работающие публичные страницы и прежний канал обращений до решения правовых вопросов | `CONSENT_FORM_ENABLED=0` / нет флага; `LEAD_PIPELINE=telegram-only` — существующее поведение, отдельно оценить трансграничную передачу имени и телефона | `PII_INTAKE_ENABLED=0`; реальные записи в CRM не принимать |
| Изолированный QA/Preview | Только синтетические данные, отдельный PostgreSQL и тестовые документы | `CONSENT_FORM_ENABLED=1`, `LEAD_PIPELINE=dual` для проверки Telegram fallback | `PII_INTAKE_ENABLED=1` на **тестовой** платформе |
| Целевой `kz-production` | Казахстанский VPS после миграции и утверждения документов | `SITE_PROFILE=kz-production`, `LEAD_PIPELINE=strict`, `CONSENT_FORM_ENABLED=1`, `PLATFORM_URL=http://127.0.0.1:<port>`; Telegram-секретов **нет** | `PLATFORM_PROFILE=kz-production`, раздельные `PLATFORM_ROLE=api` и `admin`, `PII_INTAKE_ENABLED=1` на API, `TELEGRAM_NOTIFY_LEVEL=minimal` в сервисе уведомлений |

**Критично:** `LEAD_PIPELINE=dual` не проходит защиту `SITE_PROFILE=kz-production` и для реальных ПДн не является целевой схемой. В `strict` при падении платформы нет резервной отправки персональных данных в Telegram; пользователь получает отказ, который нужно мониторить и устранять.

## 2. Реквизиты и юридические редакции
- Реквизиты сайта: `LEGAL_OPERATOR_NAME`, `LEGAL_OPERATOR_IIN`, `LEGAL_OPERATOR_REG_ADDRESS` (содержимое не хранить в GitHub и не выводить в логах).
- Временно на Vercel — установить эти переменные как Sensitive в проект `boombala` **до** публикации новой `/privacy`. На VPS задавать их в серверном env сайта.
- Проверьте на конечном URL, что RU и KK страницы показывают полные, идентичные реквизиты, ссылку на контакты для обращения и описание **фактического** маршрута данных. При последующем переходе на CRM обновить политику **до** включения новых способов обработки.
- `legal:load`: `DATABASE_URL=… OWNER_EMAIL=… npm run legal:load -- --dir <approved-folder>` (dry run), затем `--publish` только после утверждения Owner. Каждая редакция хранит русский и казахский тексты. Никаких внутренних инструкций в публичных body.

## 3. Порядок переключения на KZ
1. Создать независимые зашифрованные резервные копии, проверить восстановление и доступ к ключу вне сервера; убедиться в целостности миграции данных и прав ролей.
2. Развернуть публичный API и изолированную админку на казахстанском хосте; проверить HTTPS, WireGuard/доступ персонала, таймер outbox, `health` и применить все Production security profiles. Проверять файлы `deploy/kz/`, не переносить без изменения старые Vercel-секреты/конфигурацию.
3. Разместить и проверить актуальные RU/KK страницы сайта, полные реквизиты и опубликованные документы. До открытия форм — защищённый сквозной синтетический E2E со сверкой базы и админки.
4. Включить **сначала** platform API (`PII_INTAKE_ENABLED=1`), **затем** сайт (`CONSENT_FORM_ENABLED=1`, `LEAD_PIPELINE=strict`); проверить, что оба процесса реально запущены с правильными переменными.
5. Проверить новую заявку в `/requests`, QR-регистрацию в `/attendance`, работу минимальных Telegram-уведомлений, отказ при сбоях, доступ сотрудников и отсутствие дублей.
6. Удалить только свои синтетические записи по известным ключам. Задокументировать адреса, коммит, наличие offsite-бэкапа, активные роли и процедуру отката.

## 4. Обязательный сквозной тест
1. Через форму `/consent` зарегистрировать вымышленного взрослого с маркером `ТЕСТ`, **без телефона**, указать 3 детей, подтвердить обе отдельные галочки.
2. В `/attendance` должно быть: +1 взрослый, ожидается +3 детей, вошло 0.
3. Подтвердить вход фактически **2** детей: вошло +2, записей входа +1, взрослые не дублируются.
4. В базе должны быть две отдельные записи согласий со своими версиями. Повтор того же idempotency key не создаёт дублей.
5. Отдельная синтетическая заявка на день рождения появляется в `/requests`; в Telegram передаётся **только минимальное** служебное уведомление без имени и телефона (профиль KZ).
6. Убедиться, что ручной вход без QR работает и не требует имени или телефона. Ошибки и откаты не уничтожают исторические записи.

## 5. Мониторинг
- Наблюдать реальные плановые срабатывания таймеров/Actions, а не только ручной прогон. На KZ VPS проверить отдельный мониторинг публичного API, админки по VPN, PostgreSQL, очереди outbox и восстановления резервных копий.
- Существующие `health-check` и `outbox-retry` для старых Vercel-адресов могут не соответствовать новой архитектуре; адаптировать их после смены DNS и секретов.

## 6. Откат (без потери данных)
1. **Сначала остановить приём**: сайт `CONSENT_FORM_ENABLED=0`; при серьёзном сбое назначить `SITE_PROFILE=rollback-safe` на резервном размещении. Эта конфигурация должна отказывать всем формам, а не отправлять персональные данные за границу.
2. На платформе установить `PII_INTAKE_ENABLED=0` или вывести публичный API из приёма, сохранив БД и аудит.
3. Восстановить предыдущий рабочий релиз **на разрешённом размещении**. Старый Vercel-деплой допускается лишь для публичного контента без форм, которые принимают реальные ПДн.
4. Зафиксировать инцидент и сверить недоставленные outbox-сообщения, контрольные суммы и резервную копию; не удалять существующие записи ради «чистой» статистики.

**Запрещено:** откатывать реальный KZ Production на `LEAD_PIPELINE=telegram-only` с передачей имени/телефона через зарубежный Telegram или на `dual`, который обходит контролируемую CRM.
