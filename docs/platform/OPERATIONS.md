# Boom Bala Platform: эксплуатация (Vercel + Supabase PostgreSQL)

Статус: черновик. Production не меняется и миграции к production-базе не применяются без подтверждения владельца.

> **Персональные данные.** У Supabase нет региона в Казахстане. Пока нет отдельного решения о законном размещении, платформа
> не принимает персональные данные в production (`PII_INTAKE_ENABLED=0`), реальные данные клиентов в Supabase не загружаются.
> См. `SUPABASE-ADAPTATION.md`.

## Проекты на Vercel

| Проект | Root directory | Назначение |
|---|---|---|
| site | `/` (корень репозитория) | публичный сайт boombala.kz (как сейчас) |
| platform | `platform/` | закрытая админка + серверные API; отдельный URL (`admin.boombala.kz` или `*.vercel.app`) |

Платформа ничего не публикует для поисковиков (`noindex`), cookie сессии ставит только её origin. Сайт обращается к платформе
**с сервера** (не из браузера).

## Переменные окружения платформы (Vercel → Environment Variables → Sensitive)

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Supabase **Transaction pooler** (порт 6543), пользователь БД |
| `MIGRATION_DATABASE_URL` | Supabase **Direct/Session** (миграции, advisory lock). Нужна только там, где запускаются миграции |
| `DATABASE_CA_CERT` | PEM корневого сертификата Supabase (проверка сервера). Без него: `DATABASE_SSL=no-verify` (шифрование без проверки, риск MITM) |
| `DATABASE_POOL_MAX` | размер пула на экземпляр (по умолчанию 3) |
| `PLATFORM_HTTPS=1` | cookie `__Host-bb_session`, Secure, HSTS (всегда на Vercel) |
| `PII_INTAKE_ENABLED` | `0` по умолчанию: платформа не принимает ПДн. `1` только после решения о законном размещении |
| `PLATFORM_INTAKE_TOKEN` | общий секрет сайта и платформы для server-to-server приёма (длинная случайная строка) |
| `CRON_SECRET` | секрет эндпоинта повтора уведомлений |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | существующий чат уведомлений; `TELEGRAM_NOTIFY_LEVEL` = `full` (как сейчас) или `minimal` (без имени и телефона) |
| `PLATFORM_IP_PEPPER` | секрет для хэша IP в истории согласий (IP не хранится открытым) |

Ключи Supabase `anon` и `service_role` **не используются и не добавляются никуда**. **Data API у проекта отключить.**

## Миграции

- Только вперёд, совместимы с обычным PostgreSQL (схема `bb`, каждая миграция заканчивается `SELECT bb.harden_schema()`).
- Запуск: `MIGRATION_DATABASE_URL=… npm run db:migrate` с машины администратора, не из рантайма Vercel.
- Порядок выкладки: сначала миграция (совместимая с предыдущей версией кода), затем деплой, затем проверка `GET /api/health` и входа.
- Откат кода: Instant Rollback в Vercel. Миграции обратно-совместимы в пределах релиза (добавление, а не удаление).

## Повтор уведомлений Telegram (outbox)

Заявка сохраняется вместе с задачей уведомления в одной транзакции. Отправка:
1. сразу после сохранения (быстрая попытка);
2. «попутно» при каждом приёме новой заявки и при открытии обзора администратором;
3. по расписанию: `GET /api/cron/outbox` с заголовком `Authorization: Bearer $CRON_SECRET`. Vercel Cron на бесплатном
   тарифе запускается редко, поэтому нужен внешний планировщик (например, GitHub Actions по расписанию или платный Vercel Cron
   каждую минуту). **Решение о планировщике нужно принять до включения приёма заявок.**
Необработанные (`dead`) уведомления видны в админке.

## Резервные копии и выход из Supabase

- Рабочая эксплуатация требует платного тарифа с ежедневными бэкапами (актуальные условия уточнить у Supabase).
- Дополнительно: `pg_dump -Fc` по расписанию на независимое хранилище, шифрование, ежемесячная проверка восстановления.
- **План выхода:** схема и данные обычный PostgreSQL; перенос на сервер в Казахстане = `pg_dump`/`pg_restore` +
  смена `DATABASE_URL`. Приложение не зависит от Supabase SDK.

## Что не реализовано (честно)

- 2FA (TOTP) для владельца, восстановление пароля по e-mail (сотрудника сбрасывает владелец).
- Мониторинг и оповещения о недоступности.
- Проверка на реальном проекте Supabase: нужен тестовый проект и доступ (проверка на локальном PostgreSQL с имитацией ролей Supabase выполнена).
