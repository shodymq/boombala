# Boom Bala Platform: эксплуатация

Статус: **черновик для Этапа 1**. Развёртывание в Казахстане появится вместе с выбором хостинга; реальные команды
бэкапа и восстановления дописываются и **проверяются** в Этапе 5. Ничто здесь не применяется к production без
подтверждения владельца.

## Переменные окружения (только на сервере)

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | строка подключения к PostgreSQL (на VPS это `localhost`, порт БД наружу не открывается) |
| `PLATFORM_HTTPS=1` | приложение отдаётся по HTTPS: имя cookie `__Host-bb_session`, `Secure`, HSTS, `upgrade-insecure-requests` |

Секреты не попадают в Git (`.env*` игнорируются) и не передаются браузеру: клиентского `NEXT_PUBLIC_*` у платформы нет.

## Схема развёртывания (целевая, Вариант B)

```
Internet ── 443 ──> reverse proxy (TLS, ставит X-Real-IP, лимит размера тела)
                         │ 127.0.0.1
                         ├──> platform (Next standalone, порт 3100)
                         └──> (позже) api.boombala.kz → тот же сервис
                    PostgreSQL 16 (127.0.0.1:5432, доступ только с localhost)
```

- Приложение **не должно** быть доступно в обход прокси: IP клиента берётся из `X-Real-IP`, который ставит прокси.
- Файрвол: открыты только 80/443 и SSH (по ключу, без пароля).
- Пользователь БД приложения без прав суперпользователя; миграции выполняются отдельной ролью.

## Порядок выкладки

1. Остановка не требуется: сначала миграции (`npm run db:migrate`), совместимые с предыдущей версией приложения.
2. Новая версия приложения.
3. Проверка `GET /api/health` (БД) и входа.
4. При проблеме: вернуть предыдущий образ/сборку. Миграции только «вперёд», поэтому каждая должна быть
   обратно-совместимой (добавление, а не переименование/удаление) в пределах одного релиза.

## Резервные копии (план, реализация и проверка в Этапе 5)

- Ежедневно `pg_dump -Fc` + шифрование (age/gpg), хранение на втором носителе в РК. Срок хранения: 14 ежедневных + 8 еженедельных.
- Ежемесячно **проверка восстановления** в пустую базу (бэкап, который ни разу не восстанавливали, не считается бэкапом).
- Позже при необходимости: архивирование WAL для восстановления на момент времени.
- Доступ к бэкапам ограничен; ключ шифрования хранится отдельно от копий.

## Откат функций сайта (после Этапа 3)

Публичный сценарий брони включается флагом `NEXT_PUBLIC_BOOKING_V2` в проекте сайта на Vercel. Выключение флага возвращает
прежнюю форму с отправкой в Telegram без изменения кода. Старый `/api/lead` не удаляется до подтверждённой проверки новой системы.

## Обслуживание

- Регулярно: обновление ОС и зависимостей, ротация сессий (`purgeExpiredSessions`) и таблицы попыток входа (`purgeOldLoginAttempts`).
- Журнал действий (`audit_log`) неизменяем на уровне БД; хранить его нужно не меньше срока, установленного политикой оператора.
- Сотрудник уволен: деактивировать (сессии завершаются сразу). Удалять учётные записи не нужно: ссылки в журнале сохраняются.

## Что не реализовано (честно)

- Двухфакторный вход (TOTP) для владельца: рекомендуется после MVP.
- Автоматическое восстановление пароля по e-mail: сотрудника сбрасывает владелец (требует доверенного канала передачи пароля).
- Мониторинг и оповещения о недоступности: планируется в Этапе 5.
