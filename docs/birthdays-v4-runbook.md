## Миграции и каталог

1. Единственная миграция `017` — `017_sheets_live_sync.sql`: общие зоны и метаданные односторонней синхронизации. Удалён пустой конфликтующий `017_birthday_packages_v4.sql`.
2. `018_birthday_crm_v2.sql` зависит от 017: добавляет Booking V2 и пакетный каталог. Применять только после 017.
3. Повторно применить роли после обеих миграций, выполнить seed и `preflight` в фазе `ready`.
4. V4.2 IDs и пары base/weekday: `happy-party` 54 900/38 430 ₸; `star-party` 79 900/55 930 ₸; `boom-bala-party` 114 900/80 430 ₸. Сайт и SQL используют те же IDs, имена и цены. Seed не переписывает историю цен; несовпадение блокирует preflight.
5. Миграция оставляет старые `wow-party`, `magic-party`, `boom-party` без изменений и в прежнем состоянии продажи. Сайт V4.2 сначала публикуется после готовности backend. Только после проверки новых заявок и каталога отдельная команда `catalog:retire-legacy` архивирует старые IDs и отключает их для новых броней. Старые формы сохраняют исходный ID в заявке, но новая бронь по уже архивированному пакету не подтверждается.
6. Rollback: сначала восстановить снимок флагов каталога командой `catalog:restore <snapshot>`, затем вернуть предыдущие приложения. Брони, заявки, цены и финансовые факты не удаляются и не пересчитываются.

## Telegram и документы

- Локальный `telegram-only` API test должен использовать только mock Telegram и синтетические данные. Он проверяет точное `preferredStartTime` без округления.
- `SITE_PROFILE=kz-production` требует `LEAD_PIPELINE=strict`, URL API на loopback и запрещает `TELEGRAM_*` на сайте. При этом текущий strict payload не передаёт `preferredStartTime` в Platform/CRM.
- Production `/privacy` указывает, что Telegram получает только уведомление без имени и телефона; booking consent в коде для KZ говорит то же. Поэтому подробный direct `telegram-only` формат с именем/телефоном — только локальная проверка и не Production-конфигурация.
- QR `/consent` получает опубликованные `visit_rules` и `personal_data_consent` из CRM, показывает независимые галочки и отправляет их версии; при устаревших версиях API должен вернуть 409. На публичном `/rules` проверена V1.3, версия публикации CRM 2. Новую legal-публикацию этот релиз не выполняет.

## Sheets dry-run

После установки 017/018 и DB roles можно выполнить одноразовый `npm run sheets:live-sync:dry-run` с Viewer-only Google key, `SHEETS_SYNC_ENABLED=0` и HMAC key из защищённых env-файлов. Dry-run читает лист `Лист1`, сверяет расписание и пишет только техническую строку в `sheet_sync_runs`; он не создаёт и не переносит брони, не меняет платежи и не включает timer. Сверить конфликтные/ручные строки и 24 текущих блока с менеджером. Timer и автоматический apply остаются выключены без отдельного разрешения владельца.

## Порядок Production-релиза после GO

1. Снять новый read-only baseline, выполнить свежий backup и verifier/restore PASS; повторить upgrade rehearsal `001–016 → 017 → 018` на изолированном восстановлении.
2. Подготовить Linux x86_64 artifact точного RC SHA и проверить `RELEASE.json` плюс SHA-256.
3. На VPS применить 017, затем 018; повторно применить DB roles, выполнить seed и `preflight` (`ready`). Сверить counts и контрольные суммы старых 24 блоков, заявок и контактов.
4. Развернуть совместимый VPS API/bridge, затем Platform; проверить health, MFA/RBAC, календарь и запись V4.2 в изолированной базе/стейджинге. Публичный сайт пока остаётся прежним.
5. Развернуть сайт V4.2 последним. Проверить RU/KK, 6 серверных цен, три package IDs, формы и путь заявки без реальной тестовой заявки. Не включать прямую подробную отправку Telegram.
6. После успешного cutover и отдельного подтверждения сверки старых пакетов выполнить `catalog:retire-legacy` и `preflight --final`.
7. Синхронизацию Sheets отдельно оставить в dry-run до итоговой сверки и owner GO на включение.

## Rollback

1. Если сайт выдаёт некорректные package IDs или заявки не принимаются — вернуть предыдущий site release.
2. Если старый сайт должен снова принимать брони по legacy IDs, сначала восстановить снимок флагов каталога и убрать архивные маркеры для ранее активных legacy IDs; затем вернуть старый site release.
3. Если проблема в Platform/bridge — вернуть предыдущие совместимые артефакты, не откатывая и не удаляя additive миграции. Не запускать обратные destructive SQL.
4. Проверить сохранность aggregate counts, оплат, исторических ID и всех блокировок после отката.
