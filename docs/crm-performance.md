# Скорость CRM: замеры, причины, что изменено

Все цифры ниже получены на локальном контуре, максимально близком к production: процесс «VPS» (единственный с `DATABASE_URL`, роль bridge), процесс «Vercel» (`CRM_BRIDGE_MODE=legacy`, без `DATABASE_URL`) и логирующий прокси между ними, который добавляет заданную задержку (RTT) на каждый вызов моста. Данные синтетические: 5 000 заявок, 1 200 броней. Браузер: Chromium, прогретый контур, медиана 7 прогонов. Запуск и повтор:

```bash
npm run build
DATABASE_URL=postgres://postgres@127.0.0.1:54330/<база с миграциями, seed и пользователями owner@perf.test / manager@perf.test> \
PERF_PASSWORD=<пароль> PERF_RTT_MS=200 PERF_RUNS=7 node e2e/perf-bridge.mjs
```

## Что не удалось измерить локально

- Реальный RTT Vercel → VPS и холодные старты функций Vercel. Production-сессия требует логин и MFA владельца, входить от его имени нельзя, поэтому замер на боевом контуре должен сделать владелец (см. «Как измерить на Vercel»).
- Регион функций Vercel у проекта `boombala-platform`: **iad1 (Вашингтон)**; VPS стоит в Казахстане (профиль `kz-production`). Реальный RTT неизвестен, физически он порядка 200 мс и выше. Цифры при RTT 200 мс ниже — модель этого случая, не измерение.

## Главная причина медленной работы

Каждая страница в режиме моста делала **несколько последовательных HTTP-вызовов к VPS**, и каждый платил полный RTT:

| Страница | Было (последовательно) | Стало |
|---|---|---|
| Календарь | сессия → каталог → таймлайн → (заявка) → (бронь) → все заявки целиком | сессия ∥ один RPC `calendar.view` |
| Заявки | сессия → каталог → поиск | сессия ∥ один RPC `requests.index` |
| Карточка заявки | сессия → заявка → каталог | сессия ∥ один RPC `requests.card` |
| Обзор, посещаемость, клиенты, журнал | сессия → RPC | сессия ∥ RPC |

SQL на VPS не узкое место: 1–15 мс на RPC при 5 000 заявок (`EXPLAIN`: последовательное чтение 5 000 строк, 6 мс). Индексы и миграции не менялись.

«RPC на загрузку» считает вызовы моста во время загрузки страницы; из двух оставшихся один — проверка сессии для шапки, второй — данные страницы, они идут одновременно. Переход «Обзор» 60→90 мс: страница берётся из prefetch, разница — накладные расходы добавленной в замер проверки обратной связи, а не страницы. Реакция меню на нажатие: ~90 мс до появления индикатора (включая накладные расходы автоматизации браузера).

После правки целевые показатели (переход до 1 с, календарь до 1,5 с) выполняются даже при модельном RTT 200 мс; до правки календарь при 200 мс открывался за 1,36 с по меню и был на пределе.

## Что изменено

- `calendar.view`, `requests.index`, `requests.card`: типизированные RPC, которые отдают всё нужное странице за один вызов. SQL внутри выполняется параллельно. Календарь больше не тянет все заявки целиком (раньше это росло вместе с базой): заявки дня фильтруются в SQL, при превышении 200 показывается признак «список обрезан».
- `requirePermissionAnd` (`src/server/dal.ts`): в режиме моста запрос данных стартует одновременно с проверкой сессии. Это безопасно, потому что **каждая** операция моста сама проверяет сессию и роль на VPS (RBAC в `core/*` и в `calendar.view`); при отказе сессии пользователь перенаправляется, а результат отбрасывается. Тест `tests/bridge-aggregates.test.ts` проверяет, что роль без права получает `Forbidden`.
- `dashboard` на VPS: независимые чтения идут параллельно.
- Индикатор нажатия в боковом меню (`useLinkStatus`): ссылка сразу показывает, что страница открывается.
- Измерения: заголовок `Server-Timing` у ответов моста (проверка сессии, время обработчика, число и суммарная длительность SQL; без текста запросов и данных), логи `CRM_PERF_LOG=1` на обеих сторонах.

## Что проверено и сознательно НЕ сделано

- **Скелетон `loading.tsx`**: был добавлен и измерен, переходы стали **медленнее** (около 850 мс вместо 130 мс: React удерживает показ заглушки перед раскрытием контента). Это как раз маскировка вместо ускорения, поэтому он удалён.
- **Кеш справочников**: каталог на VPS читается за ~1 мс и теперь едёт в том же RPC, лишнего вызова нет; кеш добавил бы только риск неактуальных данных. Доступность комнат не кешируется нигде (тест `calendar.view never serves stale availability`).
- **`cache: "no-store"` в клиенте моста**: это POST-запросы, они и так не кешируются Next; менять нечего.
- **Повторная проверка сессии в каждом RPC**: стоит 0,4–1 мс на VPS. Оставлена: это граница безопасности, а не причина задержки.
- **Индексы и миграции**: не нужны при текущих объёмах. Пересмотреть при десятках тысяч заявок.

## Решение для владельца: регион функций Vercel

Каждый заход на страницу теперь стоит минимум одного RTT до VPS, поэтому оставшаяся задержка почти целиком определяется расстоянием Vercel → VPS. Регион проекта сейчас `iad1`. Ближайшие к Казахстану регионы Vercel: `fra1`, `arn1`, `dxb1`, `bom1`. Не меняйте регион вслепую: сначала измерьте RTT.

### Как измерить на Vercel

1. В Preview-окружении (не в Production) временно задайте `CRM_PERF_LOG=1` на фронтенде и на мосту.
2. Откройте календарь и «Заявки» после входа и посмотрите логи функций: строки `[bridge-client] ... rtt=…ms server="session;dur=…, handler;dur=…, db;dur=…"`. `rtt` минус `handler` — чистая сеть Vercel → VPS.
3. Если `rtt` заметно больше 100 мс, смените регион функций (`Settings → Functions → Function Region`) на ближайший и повторите замер. Холодный старт добавляет TCP+TLS до VPS (2–3 RTT) к первому вызову; тёплые функции переиспользуют соединение.
4. Уберите `CRM_PERF_LOG` после замера.

На VPS при желании увеличьте `DATABASE_POOL_MAX` до 5 (по умолчанию 3): `calendar.view` выполняет несколько запросов параллельно.
