# Birthday CRM V2 (Booking V2) и Pricing V4.2

Ветка `feat/birthday-crm-v2` построена поверх PR #64 (`codex/sheets-live-sync`, HEAD `ce45da1`). Это единственный актуальный PR CRM по Stage 2; устаревший PR #53 не используется. Публичный сайт, `LEAD_PIPELINE` и публичные формы не затронуты.

## Что сделано

- **Миграция `018_birthday_crm_v2.sql`** (следующая после 017; применённые миграции не менялись):
  - три пакета V4.2 (`happy-party`, `star-party`, `boom-bala-party`) и их цены в существующей истории `price_rules` (выходные = `base`, будни = `weekday`, праздничные даты = правило `date`, которое уже поддерживал `resolvePrice`);
  - версионируемые условия `package_versions` (v4.2: включённые дети и взрослые, аниматоры, минуты программы, 240 минут комнаты, скидка 20% на вход дополнительных детей), единый каталог развлечений `program_options` (ID и названия RU/KZ из спецификации) и правила выбора `package_program_rules` / `package_program_options`;
  - старые `wow-party`, `magic-party`, `boom-party` архивируются для новых продаж (`is_active = false`, `package_archive`); строки, история цен, брони и оплаты не удаляются и не пересчитываются; триггер не даёт переактивировать их при позднем seed;
  - `booking_cards` (карточка события), `booking_card_events` (append-only история), `guest_tariffs` (тарифы входа дополнительных гостей: **не заполнены**, бизнес их не утвердил);
  - `sheet_sync_records.state` получает значение `crm_managed` (передача записи в CRM).
- **Серверные правила** (`src/core/booking-pricing.ts`, чистые функции; `src/core/booking-card.ts`, запись и чтение):
  - выбор программы проверяется по версии условий пакета; полная проверка при «Программа согласована»; изменение согласованной программы снимает согласование;
  - цена пакета = замороженная сумма брони; доплаты: `max(0, дети − включено)`, `max(0, взрослые − включено)`; скидка 20% только на вход дополнительных детей; неизвестный тариф или состав «по факту» дают явный статус `incomplete` и пустой итог, сумму согласует менеджер вручную (ничего не выдумывается);
  - оптимистичная блокировка по `version` (`card_version_conflict`), создатель карточки не меняется, ответственный менеджер и автор последнего изменения хранятся отдельно.
- **Типизированный мост** (новые операции, старые не тронуты): `booking.card` (чтение), `booking.card.save`, `booking.handover`. Подтверждение брони принимает необязательный `card`; перенос передаёт карточку новой брони и сохраняет создателя; отмена и предоплата пишутся в историю.
- **Google Sheets**: запись, переданная в CRM, больше не управляется синхронизацией. Воркер `sheets-live-sync.ts` получил две точечные правки: строка с `crm_managed` пропускается (`unchanged`), а её отсутствие в таблице не переводит запись в `source_missing`. Контракт зон Codex (`occupancy_mode`, `occupancy_key`, `general-hall*`) использован как есть.
- **Интерфейс календаря**: карточка брони (`booking-card.tsx`), форма новой брони с полями именинника, состава и языка, история события, передача записи из таблицы в CRM.

## Порядок выкладки (выполняет Codex; production без согласования не трогать)

1. Влить PR #64, затем этот PR (stacked на `codex/sheets-live-sync`).
2. VPS: `npm run db:migrate` (применит 018), `npm run db:roles` (`booking_card_events` и `guest_tariffs` получают только SELECT/INSERT для `bb_admin`), `npm run preflight`.
3. Обновить VPS bridge на этот коммит; проверить `booking.card` реальной сессией менеджера (200 с ключами `fields`, `terms`, `pricing`, `history`).
4. Только после этого переключить Vercel frontend (merge → автодеплой). Старый frontend с новым bridge работает: старые операции сохранены.
5. Откат: вернуть предыдущий деплой Vercel; миграция аддитивна и откатывать её не нужно.

## Что намеренно не делается

- Тарифы входа дополнительных детей и взрослых и календарь праздничных исключений не придуманы. Праздничный день задаётся правилом цены `date` (`setPriceRule`), тариф вносится в `guest_tariffs`.
- Режим прямого PostgreSQL без моста и режим FastAPI-ядра не получают карточку: она работает через типизированный мост (production-режим).
- Доступность аниматоров по людям не моделируется; хранится их имя и количество по пакету.
