# Временная синхронизация Google Sheets → CRM

Источник: таблица владельца «Банкеты», лист `Лист1`. Источник передаёт полный снимок из приватного standalone Google Apps Script (GAS) по HTTPS в существующее приложение Platform на VPS. GAS читает таблицу от имени владельца; Google Cloud service account, JSON key, Cloud Billing и публикация таблицы не нужны.

Синхронизация создаёт только календарные блокировки через существующий legacy booking writer. Она не создаёт заявки, брони, подтверждения или факты оплаты. Удалённая строка никогда не освобождает помещение: она отмечается `source_missing` для ручной сверки. Владение `crm_managed` необратимо для синхронизации: никакие ошибочные, валидные, изменённые или отсутствующие строки не меняют это состояние и не меняют CRM-блок.

## Безопасные состояния по умолчанию

- HTTPS ingress закрыт, если `SHEETS_WEBHOOK_ENABLED` не равен `1`.
- Запись выключена, если `SHEETS_SYNC_ENABLED` не равен `1`.
- Vercel всегда отвечает `404` на ingress даже при случайно заданных флагах. SQL и штатный booking writer доступны только процессу на VPS.
- GAS `CRM_SYNC_MODE` по умолчанию `dry_run`; таймер не создаётся при установке ID-триггеров.
- Nginx не публикует `/api/bridge/sheets-sync`. Для доступности из GAS требуется отдельное разрешение владельца на добавление отдельного точного HTTPS location к VPS. Остальные маршруты админки при этом должны оставаться закрыты.
- Старые systemd Sheets timer/service не входят в новую конфигурацию и не должны устанавливаться.

## Установка приватного standalone Apps Script

Владелец создаёт отдельный проект на Apps Script и оставляет доступ только своей учётной записи. Не добавляйте проект в таблицу как связанный (bound) script и не делитесь проектом с менеджерами: это защищает Script Properties и HMAC secret от редакторов таблицы.

1. Создайте standalone Apps Script проект под учётной записью владельца таблицы.
2. Скопируйте `deploy/kz/google-apps-script/Code.gs` в проект и включите отображение manifest-файла `appsscript.json`; замените его содержимым из этого каталога.
3. В Script Properties настройте `CRM_SYNC_EXPECTED_SPREADSHEET_ID` и `CRM_SYNC_OWNER_EMAIL`. `CRM_SYNC_HTTPS_ENDPOINT` и `CRM_SYNC_HMAC_SECRET` не задавайте до отдельного разрешения на публикацию ingress. `CRM_SYNC_MODE` оставьте `dry_run`.
4. От имени владельца запустите `setupCrmSyncIdAutomation`. Проверьте запросы доступа: требуются spreadsheet read/write для добавления и защиты CRM Sync ID, installable triggers и Script Properties, а также HTTPS fetch. Drive scope не запрашивается.
5. Скрипт добавит защищённую колонку `CRM Sync ID`, присвоит UUID непустым строкам и установит только edit/change triggers. Проект должен оставаться приватным. Менеджерам запрещено копировать или сортировать отдельно колонку идентификатора; при копировании строк без ID скрипт выдаёт новый ID. Неоднозначные дубли ID закрываются на ручную сверку.
6. Проверьте копирование, вставку, структурную вставку и сортировку на копии таблицы. Сортируйте весь диапазон вместе с CRM Sync ID. Строки с дублированными/потерянными ID не исправляйте массовой очисткой.

Для последующей периодической полной сверки GAS использует time-driven trigger раз в минуту. Он не устанавливается функцией `setupCrmSyncIdAutomation`; функция `installLiveSyncTimer` остаётся отдельным ручным действием и запускается только после отдельного разрешения владельца.

## Защищённый ingress и протокол

Путь: `POST /api/bridge/sheets-sync` на VPS. Запрос должен быть `application/json`, не больше 256 KiB, максимум 600 строк, максимум 1000 символов в каждой ячейке. Схема ограничена известными колонками и точными spreadsheet ID / листом `Лист1`.

Заголовки `X-BB-Timestamp`, `X-BB-Nonce`, `X-BB-Signature`. Подпись — HMAC-SHA256 от UTF-8 строки `timestamp.nonce.rawBody`; timestamp допускается в пределах пяти минут. Nonce — UUID, повтор nonce отклоняется. Тело содержит постоянный `requestId`; его SHA-256 и итоговый безопасный агрегат сохраняются в webhook audit-таблицах. Повтор того же ID с тем же телом возвращает сохранённый результат; повтор с другим телом получает 409. Применение синхронизации сериализуется PostgreSQL advisory lock и идемпотентными операциями штатного writer.

Таблицы аудита хранят hash/ID запроса, исход выполнения и агрегаты, но не полный payload, имена или телефоны. Нормализованные поля источника сохраняются только в ограниченной таблице синхронизации согласно существующей модели доступа. Логи GAS содержат только режим, количества и safe HTTP/error code.

До публикации endpoint необходимы: свежая резервная копия и проверенное восстановление, применение миграций на изолированном клоне, отдельный review точного Nginx location и отдельное разрешение владельца. В шаблоне публичного сайта `/api/` закрыт; не включайте общий proxy для API. В будущем разрешается только точный POST location для Sheets endpoint на отдельном HTTPS API hostname/сертификате и проксирование к существующему VPS Platform writer. Не открывайте PostgreSQL, не направляйте этот запрос на Vercel и не открывайте остальные маршруты `bb-admin`.

## Локальная проверка и dry-run

До Production используйте синтетическую копию таблицы и изолированную PostgreSQL. Для legacy CSV планирования доступен локальный dry-run:

```sh
cd platform
node --no-warnings scripts/sheets-import-dry-run.ts \
  --spreadsheet '<source-id>' --sheet-id '<numeric-id>' --sheet 'Лист1' --csv '<local-copy.csv>'
```

Он использует read-only `READ_URL` и отдельную scratch `STAGING_URL`, если передан. `STAGING_URL` должен отличаться от источника. Этот CLI не подключается к Google напрямую и не пишет брони. Реальный GAS `dry_run` возможен только после отдельного утверждения и доступности защищённого endpoint; при `SHEETS_SYNC_ENABLED=0` календарь не меняется.

Production-проверка должна сверить строки по CRM Sync ID, статусу, room/date/time и source mapping, отдельно объяснить каждую из существующих 24 блокировок. Дубликаты, пересечения, отсутствие строки и изменения после handover требуют ручной сверки. Время — `Asia/Almaty`, длительность 4 часа, HH:00, без буфера; общие зоны используют установленную модель shared rooms. Поле предоплаты из Sheet — только заметка, никогда не финансовый факт.

## Production release sequence — только после отдельного GO

1. Согласовать freeze-окно таблицы и пользователя-оператора. Пока менеджеры редактируют таблицу, Production sync остаётся выключенной.
2. Снять свежие агрегаты и fingerprint активных блокировок. Создать backup и восстановить его в изолированный PostgreSQL; сравнить агрегаты и канонический fingerprint до релиза.
3. На восстановленной копии применить последовательность миграций `017 → 018 → 019 → 020 → 021 → 022`; прогнать PostgreSQL tests, duplicate/handover concurrency и booking E2E. Не пропускать миграции и не применять FastAPI migration sequence.
4. На Production применить тот же миграционный набор только после подтверждения restore gate. Выполнить `npm run db:roles` с утверждёнными secret values без вывода их в stdout; выполнить preflight и повторно сверить protected counts, блокировки, брони и payment facts.
5. Развернуть VPS Platform bridge. Установить `SHEETS_WEBHOOK_ENABLED=0` и `SHEETS_SYNC_ENABLED=0`; установить отдельные случайные секреты `SHEETS_WEBHOOK_HMAC_KEY` и `SHEETS_SYNC_HMAC_KEY` в закрытый VPS env. Не копировать секреты в GAS до утверждения endpoint. Выполнить VPS health/RPC smoke; проверить, что ручные CRM операции работают.
6. Отдельным изменением Nginx и только после owner GO добавить точный HTTPS POST ingress. Проверить TLS, отказ неподписанного запроса, replay 409, oversize отказ и отказ на остальных путях. Публичный endpoint не включать одним только приложенческим deploy.
7. Развернуть Platform UI через проверенный Vercel Preview. Сверить точный SHA, migration compatibility, bridge operations и no-DB-url mode. Production promotion — отдельный owner GO; merge в Production-ветку может запускать Vercel deployment.
8. После разрешения подключить endpoint/secret к приватным GAS Script Properties в режиме `dry_run`; запустить `syncSnapshotNow` вручную. Сопоставить результат с календарём и 24 исходными блокировками. Конфликты и пропуски закрыть с менеджером.
9. Запись возможна только после отдельного разрешения: установить `SHEETS_SYNC_ENABLED=1` на VPS, выполнить однократный согласованный apply. Проверить прочтением все новые/изменённые записи, сохранность старых ID, отсутствие payment facts и повторить тот же снимок для проверки нулевых дублей.
10. Для автоматической временной синхронизации отдельно подтвердить полный dry-run и запись, установить `CRM_SYNC_MODE=apply`, затем отдельно запустить `installLiveSyncTimer`. Ежеминутный полный снимок не становится активным при одном лишь деплое.

## Остановка и rollback

- Немедленно остановить запись: установить `SHEETS_SYNC_ENABLED=0`, `SHEETS_WEBHOOK_ENABLED=0`, остановить и удалить только GAS live timer trigger через Apps Script; сохранить Script Properties для расследования.
- Переключить сайт/Platform на предыдущий проверенный артефакт штатным atomic symlink rollback. Не откатывать данные прямыми SQL UPDATE/DELETE.
- Миграция 022 аддитивна: приложение можно вернуть на предыдущий артефакт с флагами выключенными; не удалять новые audit-таблицы и не выполнять down migration во время инцидента. Удаление схемы — отдельная согласованная операция после backup и сверки.
- Блокировки, платежные факты, заявки, source IDs и audit история остаются в БД. При сомнении оставить блокировку и выполнить reconciliation вручную; не освобождать комнату из-за отсутствующей Sheet строки.
- После отключения sync handover `crm_managed` остаётся источником истины CRM; возврат к автоматической синхронизации требует отдельного reconciliation и разрешения владельца.
